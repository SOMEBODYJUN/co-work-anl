# Work怎样用代码、超边和仓库持续做数学研究

本文件解释已发布实现的运行分工、资料流和目录归属。具体字段与命令见[IMPLEMENTATION](IMPLEMENTATION.md)，登记/建图启动词见[PHASE3_READINESS](PHASE3_READINESS.md)。这是运行说明，不改变任何数学Claim，也不表示全仓登记、正式图或研究运行已经创建。

运行默认是执行优先：Work收到任务后直接读取文件、启动代码、启动Solver和checkpoint。提示词只保留数学边界和必要接口；权限、凭据和网络只在命令失败时报告。

## 四个部分怎样配合

| 部分 | 实际承担的工作 |
|---|---|
| Work的模型与平台工具 | Main与Solver的推理、交流、执行工具调用；真实子代理由平台spawn/followup创建与接续 |
| Python及计算环境 | 执行Solver编写的枚举、精确核验、构造和其它计算；可选符号/优化依赖按任务准备 |
| 数学正文、登记与超边 | 正文保存完整知识；登记定位数学身份；超边解释共同前提、推导、反驳、迁移、启发与证据 |
| GitHub | 持久保存已推送资产与历史，多对话协作；Actions/Codespaces提供可选计算资源 |

模型并发和程序计算是两类资源。本实现没有用GitHub token启动模型；增加云机器CPU也没有在代码里自动增加Work的Solver数量。GitHub保存的是可重新读取的研究资产，不是模型隐式记忆。

Main的任务是送材料、收结果、提具体意见、接续原Solver、串行组织Git写入和频繁保存。每次新的数学RUN固定启动三个Solver槽位：一个`obstacle-1`障碍组和两个`full-1/full-2`成果组，三者均为`gpt-6.1-sol`、`reasoning_effort=ultra`、`fork_turns=none`；Main不计入这个数量。Solver直接解决同一个精确问题，自选方法。主要两类输入：障碍组收到完整原题/定义/已知失败边界；成果组还可按需取全部已登记成果。两组从空历史启动，不能继承Main已读的全部内容；提示词/packet不是文件系统权限隔离。平台容量不足时必须记录缺失槽位，不能静默降级。

## 一次真实研究怎样进行

1. **恢复同一问题。** 新对话恢复自己的clone，核对题目、模型、量词、当前数学状态与最后断点。Main给出准确任务，不从全部旧聊天重建题意。
2. **给三个Solver输入。** research init生成两个packet和固定三槽位运行记录；Main使用Work实际的spawn工具一次启动`obstacle-1/full-1/full-2`，保存真实agent_id。init本身不创建模型进程。
3. **按需取知识并解题。** 成果组先search看目录，再show读实际正文；context默认两跳，带出多前提超边的全部端点与条件。遇到有用方向可以继续扩展。障碍组保持约定输入，不被既有路线预先固定。数学方法没有白名单。
4. **在需要时写代码。** 可以枚举小实例、构造候选、用精确有理数检查不等式、验证策略/证书，或者运行适合本题的其它算法。没有必须先实验再证明的固定循环；能直接证明就直接证明。
5. **及时保存可接续的进展。** Solver每产生一个有价值的引理、构造、反例、失败路线、实验回执或判断，就写自己的笔记和代码/输入，Main把具体反馈送回原Solver，并立即保存run、不可变笔记副本、事件、下一步和checkpoint。保存草稿不必等其成为正式定理，也不能把多项结果攒到最后一次提交。
6. **有数学价值后写回。** 成熟结论、有效反例、可复用方法或明确缺口进入相应存档state；代码/输入/输出进入对应证据位置。新增或更新登记、超边时保留精确身份、状态和证据，不能把计算结果直接提升为一般证明。

例如在六人客户吸引问题上，Solver可编写候选搜索；找到一个低覆盖终局仅是线索。若要称原模型反例，仍需给完整目录、客户、覆盖全部有序历史的纯SPE策略以及精确核验。程序只检查实际路径、松弛LP或局部菜单时，必须如实记录其范围。没有找到反例也不是一般命题的证明。

纯证明路线同样保存：完整引理/证明及其条件留正文，超边记录诸如{A,B}共同推出C，正文中的普通算术不必全部拆成新节点。失败时保留仍成立的引理、构造技巧和具体障碍，避免下一轮重复。

## 代码在哪跑，哪些功能实际接通

| 环境/接口 | 已有实现 | 实际边界 |
|---|---|---|
| 当前Work执行环境 | 可执行仓库Python；两项既有精确数学审计实际复跑通过 | 新问题的搜索/符号/优化程序仍由Solver按题编写；没有预装和验收所有数学软件 |
| work.py research | 检索、正文、超边窗口、packet、保存、反馈事件和恢复；有端到端测试 | 当前真实全仓registry/graph仍待对应阶段产生 |
| work.py checkpoint/sync | 已实际认证、推送并确认远端；保留不同对话工作 | 只有pushed才称长期共享，本地文件存在不等于已交付 |
| tools/compute.py + `work.py research compute` | 执行research/experiments.json明确登记的数学计算并留版本、seed、精度、输出、错误和范围；命令完成后自动做一次本地checkpoint并尝试推送 | 当前只登记两项数学审计；不是任意数学问题的现成求解器；新实验必须先登记；需要共享的回执写入未被`.gitignore`排除的`research/checks/`或存档证据目录 |
| Actions | push检查、workflow_dispatch、artifact、超时、并发控制和只读GITHUB_TOKEN配置；直接PAT dispatch接口 | 当前workflow配置能跑已登记命令；workflow_dispatch需要workflow在可发现的分支；请求被接受不等于实验通过 |
| Codespaces | devcontainer、postCreateCommand、机器列表、创建/停止接口；可再配置prebuild | Codespace是远程开发/计算机，不是Work模型；创建后仍需在其中运行登记命令并取回artifact |
| 文献/网页工具 | Solver可按当前平台实际提供的检索和阅读工具查原始文献 | 不是由GitHub token授予；精确引用及定理适用条件仍须核查 |
| 其它可选软件/服务 | 可以在具体任务需要时再接入 | 不把尚未安装、未授权或未提供的工具写成已可用，不以另连账号为默认前提 |

可用的仓库能力还包括：

- 分支、提交、历史和代码审查：保存每次数学增量；可用保护规则和CODEOWNERS限制公共文件的并发写入。
- Issues、Discussions、Projects：把开放义务、批次任务和阻塞点做成可查询工作板；不把Issue正文当数学事实，正式结果仍写state和证据。
- Actions artifacts、workflow logs、缓存和并发组：保存实验回执、限制重复运行、取消旧任务；需要时可以加matrix并行运行不同参数。
- Environments、Secrets和OIDC：给需要的云端任务提供受控凭据；程序不读取或打印Secret，当前项目只使用仓库外PAT。
- Releases、Packages和Pages：发布稳定工具包、容器/依赖或只读研究导航；它们不替代Git正文和证据。
- Webhooks/API：在需要时接收工作流完成或仓库事件；本项目当前没有把事件自动升级为数学状态。

已有本地复现分别是五人局部证明36组件/47,872系数状态和positive-kernels的有限精确代数审计，不能当成六人新证明。云机器运行Python与Work直接指挥云机器也是两件不同的事。当前稳定起点是Work执行环境加Git保存；云端执行用到时再完成实际配置和验收。

## 每个数学存档内部

以下以archives/customer-attraction为例，其它存档和明确子问题沿用相同职责。路径是数学归属，不按某个Boss长期分割知识。

| 路径 | 内容与更新规则 |
|---|---|
| README.md、问题--问题.md | 问题、核心对象、可靠结果、仍未解缺口与阅读导航；实际模型以明确正文为准 |
| state/ | 定义、定理/引理、反例、方法、障碍、算法、条件结果、开放义务等完整Markdown正文。类型和真值分开，一页可含多个可定位对象 |
| tools/ | 本问题可复用的搜索、判定、核验或其它实现 |
| tools/evidence/ | 必要源程序、参数、数据、证书、输出、精度及复现说明，由数学对象引用 |
| evidence/ | 部分存档已有的证据位置；保留现行引用，不能为了统一目录自动搬动或重复复制 |
| workspaces/BossN/ | 实际数学研究的个人工作区；内部Solver分别写自己的文件，Main在此汇总与保存候选 |
| papers/ | 成熟论文、稿件及相关材料，不把每段草稿都当论文 |
| map/ | 本存档派生图及明确分配给这里的边/整合材料；边正文按任务规定只存一份，不在全仓/存档重复维护同一事实 |
| subarchives/<子问题>/ | 同一父问题中有独立模型/范围的子档，同样保留正文、证据、工作区和图；目录从属不自动构成数学蕴含 |

全仓tools/evidence/也保留了既有冻结/比较证据。当前不是所有旧材料都已进入完全统一位置；以现行来源/对象引用为准，本轮不机械搬移。后续新资产先找到其数学owner与归属，避免再堆重复包装。

## 研究接口中按阶段产生的文件

| 路径 | 何时产生、做什么 |
|---|---|
| research/registration/inputs.json、baseline.json | 2.5第三步启动时，明确第二步实际出口及冻结版本 |
| research/registration/batches/、batches.json | 分批登记产物及汇总清单；处理者写各自批次，总集成人汇总 |
| research/registry.json | 2.5第三步形成的对象ID、版本、正文/证据位置、材料去向和精确状态总表 |
| research/operations/<run>/run.json、people/ | 登记/建图阶段配置及实际启动后的身份记录；目前有配置不代表已创建people |
| research/workspaces/<workflow-run>/<Boss>/ | 登记与建图的工程工作区，与数学存档个人工作区及旧清洗工作区分开 |
| research/runs/<run>/run.json、packet-*.json、notes/、events/ | 实际数学运行的两类输入、当前Solver、不可变笔记、反馈/接续链和恢复位置；不取代存档中的正式正文 |
| map/edges/或任务明确的存档map路径 | 有解释的关系JSON；registry.edge_files指向唯一正文 |
| map/tasks/、map/receipts/ | 分批构图的任务、写入范围、领取、覆盖和真实已推送交付 |
| map/coverage.json、map/integration.json | 逐对象覆盖及存档内跨批/跨档整合记录，最终生成前验收 |
| map/graph-v2.json、archives/.../map/graph-v2.json | 从正文、登记和关系生成的全仓/存档/子档投影，可重建，不是单独的真值来源 |
| research/experiments.json | 有意登记的可复现计算入口；新实验明确命令、输入、seed、精度和范围 |
| research/checks/ | 工程验收记录，不作为数学结论节点 |
| validation/ | 临时本地输出；不作为研究入口或长期状态。需要共享的计算回执写入`research/checks/`或数学owner证据目录后checkpoint |

当前graph.json、research/schemas及部分templates仍含旧原型，保留兼容/追溯。新流程以PHASE3_READINESS、IMPLEMENTATION和对应已实现程序为准，不能把旧图当全仓正式超图。上述登记、运行、任务与v2图文件在实际阶段执行时产生；空目录不需要预先造满。

## 整个项目怎样持续推进

第二阶段整理原来源 → 2.5第一步材料定性与目录 → 2.5第二步对象群数学整理 → 2.5第三步登记 → 第三阶段解释关系与分层图 → 自由数学研究及持续写回。

研究启动后，新成果沿同一制度回流：先保存可接续的workspace和证据，再按实质内容写入state，更新对象登记和有关超边及导航，及时checkpoint。无需每获得一条新引理就重做整个清洗流程；改动只影响相关对象和关系的定向复核。

每个Boss独立clone，共用现有文件分支和对应公屏；共享阅读，写入范围互斥，同clone Git串行。重要进展、明确障碍和中断前都保存。原Solver收到具体反馈继续；失去原进程时从相同profile、packet、笔记和下一步恢复替代者。恢复的是已写下的数学工作，不保证还原平台进程或未保存推理。

已设置的是可运行的协议、启动词、目录归属、检索/保存/协作接口与工程验证。各问题真正的最终登记、正式关系图、实际Solver团队和需要时的云端环境仍按用户启动指令及真实数学输入产生。协议准备好、程序测试通过与数学问题已解决分别报告。
