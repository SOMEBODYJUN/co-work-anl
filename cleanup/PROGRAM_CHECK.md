# 清洗程序实测与修复

本轮按用户要求测试实际使用流程，修复后部署到既有rebuild/research-v2；没有新增远端工作分支，没有替清洗者完成数学语义处置。

## 已复现并修复的问题

- 同prefix连续领取：旧程序两次都返回同一源ID，新程序只领取无人认领的下一批；空范围返回status=empty。恢复已领批次用clean list --owner self。
- 本地列表过期：旧程序领取虽已推送，但本地progress仍为空。新根程序在claim/done/release成功后自动同步，保留暂存、未暂存与未跟踪草稿；遇本地恢复冲突仍明确保留status=pushed，并另报local_sync.status=needs-attention及备份信息。
- 子存档输错后难以纠正：校验子存档存在后才写入存档绑定，首次失败后可用正确子存档重试，不冒改已有有效绑定。
- 启动重复同步：新clone使用浅克隆；下载附件向仓库根程序交接时传递经路径、HEAD、分支、程序指纹核对的一次性同步回执，避免重复fetch。旧clone正常启动仍会同步。
- 事务反复下载：清洗事务复用本clone的Git对象缓存，各事务仍用独立写入工作树、正常推送与远端确认。
- 列表上下文过大：默认只给ID、路径、状态、owner；--full保留完整元数据，--available筛未领项，--owner self恢复本人工作。

## 验证

18项真实Git工作流测试全部通过，输出见[完整测试记录](program-check-tests.txt)。覆盖6个清洗者并发领取、同项排他、连续批次推进、正文已推送才能勾选、自动同步保留草稿、恢复冲突不误报远端失败、浅克隆读旧源与checkpoint、增量指纹及重复ID、分支/角色/子档稳定性和地图门槛。

真实GitHub冷启动完成；浅克隆阶段Git目录由84,535,512字节降到1,992,381字节，但该次耗时18.176秒到15.933秒，促使进一步修复bootstrap重复同步。最终部署后再用新的独立clone复测；没有把下载量下降直接当作同比例耗时改善。每次测量的环境、退出状态、耗时及范围见[实际证据](program-check-evidence.json)。

同样显示5项来源，默认输出由2533字节减至549字节（减少约78%）；完整元数据可用--full取得。耗时是本环境单次测量，不是普遍性能保证。

所有并发领取和完成写入测试均在隔离本地Git远端进行；真实仓库只验证启动、读取及程序部署，数学来源仍10921项、语义完成0项、无人被测试占用。

## 使用

新对话使用更新的work.py和02清洗提示词。已有clone先运行根work.py sync，再继续用根程序。查看本人批次用clean list --owner self，领取新批次用clean claim --prefix 实际路径 --limit 合适数量；收到pushed及local_sync.synced后继续。needs-attention时先处理保留的本地恢复冲突，不要把已成功的远端操作当失败重复执行。
