# 资源范围与处置

本文件是对八个已冻结来源版本的语义合并。它们主要是协作协议、产品设计和工程证据，不是 Q-CAG-HALF-6 的数学证明；因此归入 `tools/evidence/cleanup`，而不是伪装成某个数学定理。相同路径的 `legacy-cleanup` 与 `main` 快照逐项比较后，保留一份对象身份，同时在来源字段中保留两个冻结提交。`CLEANER_START.md`、`CLEANUP.md` 和 `collaboration/README.md` 是旧清洗入口；新版 `cleanup/README.md`、`tools/README.md`、`AGENTS.md` 及固定 Boss 编号协议已经覆盖其中若干启动细节。

## 仍可复用的清洗合同

旧入口最有价值的内容是“语义清洗”定义：每个来源必须实读，比较全仓的同一对象与后续纠错，保留定义域、量词、假设、真实结论、关键论证、证据和缺口；候选、完整证明、条件结果、有限实验、方法障碍和原模型反例分开；一源可以拆成多个对象，多源可以合成一个自足正文。程序字段和索引只能检查记录完整性，不能代替数学判断。正文应说明用途、适用条件和后人接续接口；程序、输入和精确运行证据另放证据目录。

这些原则与当前阶段二协议一致，因此继续作为协作知识保留。当前六人目标仍必须保留有限单位客户、有限非空共同目录、六名提供者、完整有序历史、重复/空主题/零客户/任意平局，并把其他模型分开；旧稿中关于“清洗完成后再接 Solver”的流程描述不改变当前工作范围。

## 已被新版协议覆盖的历史启动细节

`CLEANER_START.md` 和 `collaboration/README.md` 假定旧的 `cleanup/research-foundation-20261028` 文件分支、旧公屏入口和程序随机生成 actor；这些细节不能继续作为当前启动合同。当前分支是 `rebuild/research-v2`，公屏是 `wcg/board-cleanup-20261028`，新对话必须显式 `--actor Boss编号`，认证与实际写端点验证通过后才能认领。旧材料没有被删除，因为它解释了历史迁移和为什么新版程序拒绝随机身份；本对象不把旧默认值写回现行入口。

旧入口还把 `research/current/...` 作为正文根目录。结果分支的现行对象协议已迁移到 `archives/<save>/state/<type>/`，并以稳定 ID、MATEK frontmatter 和 `source:<commit>:<path>` 作为承重引用。若旧路径仍被后续对象引用，引用必须按实际文件存在性迁移，不能只复制旧导航。

## 研究工作台总稿的有效设计状态

`AI_Co_Mathematician_master.md` 是一份大范围设计总稿，不是已完成产品规格。逐节读取后，其可复用结论如下：

- 研究状态应保存猜想、frontier、条件性结果、障碍、冲突和失效关系，而不只保存最终定理；关系可以是多对象超边，并为每个参与对象说明角色。
- 数学状态、执行树和协作公屏是不同层次。版本修订应追加 revision 和当前有效头，不能静默覆盖；公屏是成果、进展、警报和求助的投影，不是第二个数学事实库。
- 数学 Agent、组织协调、专业检查、程序执行和人类控制有不同权威边界。研究路线可以动态分叉、组队、交接和暂停；未验证局部引理可以条件性使用，但必须保留证伪义务和适用范围。
- 重大成果需要与声明匹配的独立检查；当前稿明确“不使用 Lean”，也没有把固定数量的审查 Agent 当作证明。价值调查、文献提取、失败研究和等价仲裁都应保存其实际范围。
- 总稿多处标注“已确认、设计展开、候选、未决、已覆盖”。这套状态词防止把设计建议写成用户裁决；对施工有影响但未定的版本、权限、删除、结案和人类确认合同，必须继续标为未决。

总稿还明确承认微观实现未闭合：它没有证明某个 UI、后台暂停、自动唤醒、专家库或跨 Project 版本协议已经存在。因此本资源只保存设计意图与边界，不把它升级为代码能力或数学结果。

## 大规模协作稿与当前载体适配

`large_scale_research_collaboration.md` 的后续裁决是沿用现有可用公屏，增量增加个人工作区、提及和双方私聊；没有部署新的独立消息服务。工作区用于隔离草稿和定向发布，公屏用于可见成果/警报/求助，私聊用于定向接续。它要求单独测试并发保存、乱序/重复/重试、接收者重启、跨存档隔离、资产批量提交和实际负载，不能以一次小批写入声称可扩展。

`work_github_adaptation.md` 将上述设计映射到人工 Work 对话和 GitHub：人类是最终控制者，Boss/清洗者负责共享正文整合，Git 分支与公屏分离；checkpoint 的明确路径和 `status=pushed` 是远端可见性的边界；旧历史、未提交草稿和数学事实不能靠摘要替代。它同时保留了真实局限：手动 Work 不能提供自动后台继续、硬暂停全部工具或生产级通信吞吐，需把这些作为未实现能力。

## 工程证据的真实范围

`evidence/README.md` 规定证据按题目和运行类型分开保存，输入、代码提交、检查器版本、命令和 Python 版本应随新运行记录；旧冻结 JSON 缺失这些元数据时，只能作为可重跑的结果概述，不能事后伪造完整封存。单实例证书和有限审计不能升级为普遍上界或外部复核。

`active_topic_routing_release.json` 记录一次工程回归：109 个协作测试通过，后续元数据修正后另有 21 个定向 `work.py` 测试通过；源文件 SHA、入口映射、路由检查和 384/406 个本地链接检查均被保存。证据覆盖的是已声明版本的本地 Git/模拟板路由行为，不是生产环境吞吐、跨 Work 自动控制或数学结论。它明确说明：当前主题与 legacy shared 的入口不同、待处理消息保留原主题、直接调用底层 board 时必须显式选择 save；这些是工程合同，不能作为 Q-CAG-HALF-6 的数学证据。

## 接续与未决项

后续阶段可以直接引用本资源来解释：为什么要先 checkpoint 再 done、为什么来源版本要带冻结提交、为什么数学对象与公屏消息分开、为什么当前阶段不把旧图自动导入、为什么不能把有限回归当成全称证明。若要把总稿继续施工，应先补齐版本吸收、删除依赖迁移、结案签署、暂停/注入事务、跨 Project 共享和生产通信容量等未决合同；不能以旧设计文字自行选择实现。

本资源不引入任何数学超边，也不替代第三阶段关系判断。其唯一的数学关联是为后续清洗者说明研究状态、来源证据和协作权限的边界；若没有已读的具体数学对象，不应从这些设计文档推导 Q-CAG-HALF-6 的真假。
