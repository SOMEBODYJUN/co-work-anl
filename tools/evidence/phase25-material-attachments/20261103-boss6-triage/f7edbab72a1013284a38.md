# 779B的加载、全局重定向与文件副作用

HERE为原`R-d398.../next_general`，WORKSPACES=HERE.parent.parent指到共同`customer-attraction`工作区父目录。SOURCE固定为其下旧R-a0的`direct_global/static_matching_independent_audit.py`，不是本JSON或新作者实现。

1. `runpy.run_path(SOURCE)`加载旧脚本；旧脚本有main guard，默认run_path不先触发该guard。因此此时只得到其函数/常量。
2. 包装器直接修改`namespace['main'].__globals__['OUTPUT']`为自己的`next_general/old_static_matching_replay.json`。改的是函数实际使用的globals，不是只改返回namespace的同名键；旧SOURCE和其BASE仍保旧位置。
3. 显式调用旧main一次。它仍读旧R-a0/static_matching证书，运行原完整定义核，把原23字段报告写到新的OUTPUT，再打印删掉queries的旧概要。
4. 包装器读这个新OUTPUT，加`this_round_provenance`一项，再以indent2及末尾换行覆盖写同一OUTPUT。包装器本身不另打印扩充后的报告。

所以源设计不覆盖旧作者3789B输出，但会两次覆盖本新输出；中断可能留下未附来源项的原23字段结果。stdout既无24条queries，也无最后附加的provenance，不等于3966B文件。包装器无main guard/参数解析，import或`--help`仍会触发旧main全循环及覆写；不能为“只取函数”导入它。

运行闭包恰需未改包装器、旧4852B代码及旧32574B输入，按两个R目录的原相邻层级恢复；3789B报告只是比较基准，不是运行输入。只把779B移到本证据original目录不保其父路径约定。所有必要原件已有单份保存，确切源ID/SHA/路径见[复用路由](<../../../../archives/customer-attraction/tools/evidence/general-root-ledger-and-old-static-matching-six-primary/related-source-routing.json>)。
