# 完整覆盖舍入障碍与可丢弃版本边界

## 来源和实际读取

本审查实读同一字节版本的两个历史路径来源：

- 稳定源 ID `b10be5532044e3323f37`，原路径 `history/retired_topic_selection/independent_review/evidence/runs/topic_selection/complete_rounding_capacity_counterexample.json`，大小 445 字节，SHA-256 `4c8f98300bbaa4d68b66e11555b3b857d517f71d2a7a69701f2bc95e6e491269`；
- `legacy-cleanup` 提交 `68fad804ec5946cb296f77dc5b336308a66abf12` 与 `main` 提交 `aefc58eac3fc6eb5d7a47d087dd2c62b5aa9974c` 均指向该路径版本。

原 JSON 已逐字段导出到 [`complete_rounding_capacity_counterexample.json`](../../tools/evidence/retired-topic-selection-20261031/complete_rounding_capacity_counterexample.json)。相关核验页把它列为“精确可分解与完整整数可行性区分”的导入合同反例；两容量 BMKP 候选稿和独立反方稿均明确引用同一边界，并把它与允许弃置物品的候选舍入分开。

## 精确对象、量词与证书

这是一个只有一个物品的容量分配实例。物品重量为

\[
w(e)=2,
\]

利润为 \(p(e)=1/100\)。有两个容量均为 1 的箱，记为 \(B_1=B_2=1\)。分数方案令

\[
x_{e1}=x_{e2}=1/2.
\]

因此两个箱的重量都为 1，且分数方案对每个箱贡献利润

\[
(1/100)(1/2)=1/200.
\]

JSON 的 `fractional_feasible` 为 `true`，`targets` 为 `[1/200,1/200]`，正好记录了两个箱的分数目标。若合同要求每件物品完整地选择某一个箱（整数变量只能为 0 或 1，且这一个物品必须被覆盖），则把它放入任一箱都会产生重量 2，超过容量 1。因此 `complete_integer_feasible` 为空；不存在满足两个硬容量和完整覆盖的整数分配。

这个推导是穷尽性的：只有“放入箱 1”“放入箱 2”两个完整整数选择，两个选择都违反对应容量。它不是随机实验，也不依赖浮点误差。

## 结论等级和失败机制

**完整证明的有限反例。** 在精确分数输入、两箱容量均为 1、要求全部物品必须整数覆盖的合同下，分数可行不蕴含完整整数可行。反例的失败机制是单件物品重量大于每个箱容量；分数解通过跨箱拆分隐藏了这个超容量事实。

**被否定的合同。** 不能把一个需要“每件物品总分配量恰为 1”的 LP 舍入引理直接当作两容量 BMKP 的后处理，除非该引理另有边界条件保证每件物品至少有一个可容纳的整数箱，或允许丢弃/未分配物品。尤其不能从一个单容量、单预算舍入结论自动推出两个精确容量预算的完整覆盖版本。

**未被否定的目标。** 原候选 BMKP 问题允许物品不分配；其近似目标是每个箱的利润达到阈值，而不是让每件输入物品都被某个箱接收。`discard_variant_not_refuted: true` 记录了该范围边界。该 JSON 不构造一个允许弃置版本的利润近似反例，也不否定母论文的主定理。它同样不证明任何允许弃置舍入算法，只是排除一个过强的中间合同。

## 与两容量候选算法的关系

实读的 `generalized_assignment/TWO_CAPACITY_LEMMA.md` 将 cheap 物品的 LP 约束写成每件物品总分配量不超过 1，并用独立的“允许丢弃”极点舍入（每个箱损失至多若干小利润物品）替代完整覆盖版本。该修正保留了未分配物品的模型语义；本源只验证修正的必要性，未验证其极点秩计数、短箱匹配或母文 profile 前提。

独立反方稿把同一个输入称为“母 Lemma22 字面全覆盖子合同的直接障碍”，并明确写出：不应由此声称 BMKP 主定理错误。该比较关系可接第三阶段的关系图：

1. 完整覆盖舍入合同 ⟹ 被上述有限证书否定；
2. 允许弃置的 cheap 舍入合同 ⟹ 不被该证书触及，但仍需独立证明；
3. 两容量 BMKP 全算法 ⟹ 还需要 profile、联合类型、short matching 和 OPT 网格等其他步骤，不能由本反例单独判定。

## 可复现材料、缺口和后续

原件已按字节保存；本批没有重新运行历史脚本，也没有把 445 字节 JSON 当作一般化程序。若后续要验证允许弃置版本，应另建含至少一个可容纳物品和一个超容量物品的实例，明确目标箱利润、物品是否可弃置及 LP 舍入是否允许删边；不能把本例中 `targets` 的正利润要求误读成“每个物品必须使用”。

本源没有外部同行审查或新颖性认证，只有有限精确证书。它的独有内容是对“完整覆盖”字面合同的最小反例及精确分数目标；去向是本审查正文和证据目录，不并入 BMKP 算法定理。
