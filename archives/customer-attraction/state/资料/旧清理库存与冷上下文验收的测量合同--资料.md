# 原verify_context.py究竟检查什么

脚本有main guard，按自身parents[4]定位原根。它读取真实Git树和原固定基线，核113个根README哈希是否保持，检查当前文档中的相对链接目标，比较7个文件字节，并要求evidence/examples/customer_attraction的git diff为空。

相对链接扫描跳过代码围栏、协议链接和纯anchor；只确认目标路径存在，不验证锚点、不读目标全文、不核数学证明。1940个链接PASS因此不是1940份证明PASS。729个(i,l,e)三元组来自0至8各9值，做精确有理式/分母检查，亦不是729游戏的SPE检查。

原脚本将结果打印成JSON，不自行写context_verification.json。保存报告额外含software_checks，其中26个work集成测试、14个路由测试、7项checks及一次未登记临时文档应拒绝；这些字段**并非该5280B脚本生成**。本18主源没有每项测试完整stdout，所以保为历史补充报告，不能声称由此原入口复现或本轮全部通过。

迁移后的archive树、当前Git基线和新actor集合已经不同。把原程序照搬到当前clone必然会量另一个对象；无需为了让旧数字PASS而伪造Git元数据或改当前文档。后续若要重测，应另立新基线、明确相同文件集合、保存真实命令和全部输出，并和本历史测量分开。

# 冷上下文审查的八个问答合同

原冷读只读8份短入口，检查76个目标链接；它没有全文复核每个目标。八个验收问题分别是：

1. 当前模型是否为有限单位客户、完整历史共同目录、终值均分；
2. 五人证据应分作者报告、完整定价与配对精确认证哪些等级；
3. S52实际前缀为何否特定新增覆盖归纳，而不否half；
4. 净缺口须保L−E为何不能删E；
5. 真实静态安全值v为何不能替换为任选i.i.d.值；
6. count缓存、waterfill代数和必要模板各自不等于完整策略资格；
7. 分数覆盖乘积为何需补小人数边界；
8. 一般共同付款到底哪一行仍未支付。

它实际推动两处概念修正：τ≤7/2不能直接跨过m4；剩余r包括当前位。它证明这些入口能引导那次受控冷读，并不证明所有无上下文读者都能独立重建全仓证明。本轮没有新增冷读代理，也没有把父子共享上下文审阅叫盲审。
