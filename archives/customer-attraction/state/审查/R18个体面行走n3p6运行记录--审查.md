# 记录字段的数学含义

生成器从 `cone_walk.Engine` 构造有限客户权重和策略锥。每一步选取一个目标终局计数向量 `target` 和动作 `a`，由 `eng.strategy(target)` 得到偏离行矩阵 `G`，再对两个组合目标 `J` 分别解浮点 LP：最大化 `objective·x`，约束 `Gx≥0`、`norm·x=L`、`x≥0`。因此记录中的 `value` 是一次浮点 LP 目标值，`rows` 是该策略的偏离行数，`J` 是所用组合目标的主题索引，`target` 是六维终局计数向量。

脚本只有在 LP 候选可由 `recover` 恢复为非负有理克隆向量、并通过 `verify_canonical` 的精确检查时，才计算实例的精确比值 `OPT/u`，更新 `best` 并写出单独的 `individual_face_walk_n3p6_best.json`。所以运行 JSON 的 `best="5"` 是生成器恢复出的精确最佳比值；它不是 2901 个 `value` 字段的最大值，也不是一个由运行日志单独给出的普遍定理。

`individual_face_walk.py` 的算法生成 `best` 文件时，会调用 `counterexample_search/cone_walk.py` 的 `Engine`、`baseline` 和 `verify_canonical`；本审查只把该脚本作为生成机制和语义来源。`individual_face_walk_n3p6_best.json` 是独立的精确见证对象，应单独记录其客户实例、策略证书和 `OPT/u`；本运行记录不重复吸收那些字段。

运行记录支持“在该有限实例和该随机走法中，已找到阈值比值 5 的精确候选”这一事实。它不能推出六人 Q-CAG-HALF-6 的半覆盖结论，也不能证明任意输入存在或不存在 `OPT/(2n−1)` 桥。`best=5` 只说明这次搜索没有发现严格超过阈值的已恢复见证。

# 后续用途与缺口

可复用的是可审计的运行合同：固定参数和 seed，保存每条 LP 记录、策略行数、目标索引，并把精确恢复出的最佳比值与浮点候选分开。若要形成数学结论，应对同一候选保存有理克隆向量、完整策略证书和逐历史效用核验，再与 `best` 文件及其他 n、p 运行比较。

仍缺少跨种子覆盖、对所有客户权重与策略的量词、LP 对偶证书和复杂度界。后续不得把日志中的均值、记录数或浮点尾数升级为定理；需要将该对象标为有限实验，直到独立正文完成全称证明或精确反例。
