# 周期菜单修复与独立交叉核对

## 1. 对象和证据等级

这组三份 JSON 输出处理一个菜单修复/周期抽取接口：给定机器菜单和非负有理弧权，先从菜单中寻找可修复的 batch/cycle，再检查 fanout、ring 和 padded-fork 结构的实际负载。它与[有界重数克隆接线与共同循环坍缩](../定理/有界重数克隆接线与共同循环坍缩--定理.md)使用相近的周期图语言，但本批本身只认证列明的审计输入与 extract_cycle 函数，不重新证明该定理的配置投影或共同循环族。

三份原始 JSON、尺寸、SHA-256 和冻结来源保存在 [source-manifest.json](../../tools/evidence/cyclic-menu-20261030/source-manifest.json)。本轮用 `clean show` 取得每一文件全文，逐字段阅读主修复、相对源的冻结交叉核对和独立图审计，并检查它们是否把 synthetic arc weights 当作一个真实调度实例的自动产物。三源均没有这样声称。

## 2. 主 cyclic batch repair 审计

`ad960c...` 状态为 `passed`，Python 3.12，Fraction 算术，seed=613513。其有限范围包括：

* 720 个显式 menu comparisons；
* 86 个 random optimizer cases，逐例保存成功迭代次数；
* fanout 族 (k=1,2,3,7,31)，每例两次迭代并输出终端菜单弧数。负载分别为
  ( (1,1,1))、( (3/4,3/2,3/2))、( (2/3,5/3,5/3))、( (4/7,13/7,13/7))、( (35/62,58/31,58/31))；
* ring 族 (m=2,3,5,9)，各自两次迭代、最终 makespan=1；
* 一个 actual padded-fork optimizer，输入哈希保留，迭代次数为0；
* 五个 fork-stagnation 参数 (1/2,1/3,1/7,1/31) 以及超大分母 (1/1208925819614629174706177)，都在初始 makespan (3/2,5/3,13/7,61/31) 或相应大分数处停滞；
* 3 个 boundary 和 6 个 invalid cases。

`robust_claim_applicable` 在这些 fixture 上均为真，但这只说明程序对自己声明的 robust 分支执行了该路径。主文件的 limitations 明确写出：有限精确测试不等于一般证明，没有 universal approximation ratio，也没有 generic LP solver 或 LP-initialization theorem。特别是 fork-stagnation 的零迭代结果说明某些输入已落在当前修复器的固定点；它是算法边界和回归见证，不能被描述成“所有 padded fork 都可修复”或“周期修复总能降低峰值”。

fanout 的输出还显示 `terminal_menu_arcs` 从6增至180，说明菜单规模随 (k) 增长；ring 的弧数为 (2m)。因此，若后续需要声称一个显式输出大小或多项式时间界，必须同时控制菜单弧数量和迭代次数，本批没有给出这种复杂度分析。

## 3. 冻结相对源的交叉核对

`be4729...` 是对相对源 `tests/audits/unrelated_machines/cyclic_batch_repair.py` 的冻结交叉核对。它使用另一个 seed=613516，在机器数 (m=2,3,4) 各生成1000个菜单，每个菜单三次独立比较，共9000个 independent frozen menu comparisons，其中 positive comparisons=3032。权重分子为0到12、分母5，margin values为 (0,1/5,7/6)，每个 ordered distinct pair 的弧数由 `rng.randrange(3)` 生成。

这份输出的独有作用是核对 `extract_cycle` 的有限行为与相对源的代码/哈希一致；它不是对 DP 或 full optimizer 的审计。文件明确列出三个限制：有限精确抽样不能证明一般 extraction theorem；合成非负有理 Arc 权重未必来自一个 scheduling instance；只有 extract_cycle 被攻击，DP 和完整 optimizer 没有被检查。因此 positive comparison 计数可作为回归数据，不能作为周期提取全称定理或端到端算法认证。

## 4. 独立显式菜单图审计

`b675256...` 是不导入作者程序的 independent graph audit。它用 seed=613512，生成3000个 random explicit menus，机器数为2到4；其中1028个含有 strict machine simple cycle。输出状态为 `passed`，但限制明确写出这是有限 independent graph audit，且 removal/arrival 权重未必来自一个真实 scheduling instance。

这份源与 `be472...` 的关系是互补的：前者复核相对源码中的 `extract_cycle`，后者独立检查显式菜单图中是否出现严格的机器简单环。两者不能合并成“任意菜单必有可抽取环”，也不能以1028/3000的比例估计任意输入的概率。它们共同保留一个清晰的结构边界：cycle extractor 的测试域是合成有理菜单，而真实调度编译还需要额外证明输入映射和弧权合法性。

## 5. 与已有对象的关系

* 与[有界重数克隆接线与共同循环坍缩](../定理/有界重数克隆接线与共同循环坍缩--定理.md)的关系是周期/置换语言和“共同循环”构造的有限回归。已有定理证明了明确的 c-wiring 配置投影与共同 cycle 族；本批的 fanout/ring/padded-fork 修复器没有扩大该定理的 (c)-wiring 量词，也没有证明一个新的 wiring 存在性。
* 与[周期峰值与稀疏流增量证据](周期峰值与稀疏流增量证据--审查.md)的关系是都保留长环、有限峰值和有理参数边界。前批的 sparse-flow 数值依赖相应原文的不等式族；本批只测试另一个菜单修复接口，不能把两种迭代器的停滞/成功行为互相替换。
* 与配置、Hall 和联合匹配审计的关系是都使用有限菜单或弧权证书。这里没有建立 Hall 流、LP 初始化或一般 approximation ratio；正的 cycle 比较只证明列明的合成权重输入通过当前函数。

后续如果要把该接口用于一般 unrelated-machines，应先证明：真实输入如何生成合法非负弧权；菜单弧数和迭代次数如何受输入位长控制；extract_cycle 与 DP/完整 optimizer 的端到端正确性；以及 fork-stagnation 情形是否有可接受的 fallback。三源均未承担这些义务。

## 6. 逐源处置

三源均已全文阅读、原字节保全并与全仓周期、配置、克隆接线和菜单审计比较。`ad960...` 作为主修复回归，保留 fanout/ring/padded-fork、停滞和边界；`be472...` 作为对相对 `extract_cycle` 的冻结交叉核对，保留9000次比较和合成弧权限制；`b675...` 作为独立显式菜单图审计，保留3000菜单和1028严格简单环。三者合并到本审查对象，不把有限通过升级为一般周期提取、LP、调度优化器或近似定理。
