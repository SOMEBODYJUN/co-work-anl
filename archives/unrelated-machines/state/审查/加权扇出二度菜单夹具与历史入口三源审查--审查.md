# 加权扇出 profile star（`0c3bf6d24f1ba76ead00`）

冻结文件 `weighted_fanout_profile_star.json` 给出一个 `6×4` 的有理矩阵 `p`，参数为

\[
T=7/3,\qquad a=0,\qquad S_1=(0,0,0,0),\qquad S_2=(1,2,3,4).
\]

第一行是

\[
(0,7/18,7/9,7/6),
\]

其余四个非空行各只有一个 `7/3`，分别位于第 0、1、2、3 列；第六行全为空（均为 `null`）。因此五个非零行的行和都恰为 `T=7/3`，空行行和为 0，总共有 8 个有限 entry，有限值集合为

\[
\{0,7/18,7/9,7/6,7/3\}.
\]

源另给 `outputs=[1,2,3,4,5]`、`missing_subset=[1,2,3,4]` 和四个有理 `beta` 值

\[
\betain\{1/10,1/5,3/10,2/5\}.
\]

按同一 profile 合同重算，若使用形如 `(2-β)T` 的边界表达式，四个参数给出 `133/30`、`21/5`、`119/30`、`56/15`；这只是该夹具字段的代数派生，不替代完整扇出证明。校验脚本确认矩阵尺寸、所有非空项的非负有理性、五个满 `T` 行、空行、`S1/S2`、输出列表和 `beta` 序列逐项相符。

与《零缺陷陷阱与加权扇出边界双源审查》比较，已有审查覆盖的是三/多主机 weighted fanout profile 的实际 YES witness、missing-one splice、`T(2-β)` 合同以及更大规范/独立运行计数；本源没有 `mu`、没有调度输出或 unknown-YES 搜索。它只是把一个小 profile 的原始 `p,S1,S2,T,beta` 输入保存为可复验夹具。不能从这个 star 输入推出任意树、任意 host、跨模块容量或一般 unrelated-machines 的近二结果。

处置为 `integrated`，目标为本页和 evidence 原件/校验；现有加权扇出证明的适用条件与“有限 profile 不等于全称算法”边界保持不变。

# 五个 weighted menu 联合夹具（`b88c0af63e1cab4774d1`）

`weighted_menu_joint_fixtures.json` 有五个命名 case。每个 case 给资源名称、组、状态和非负有理 incidence；state identity 属于输入合同，空状态与重复状态不能折叠为同一个数学对象。

## `joint_bad_heavy_yes`

资源为 `h,x,y`。`g0` 有 `heavy` 状态（唯一 incidence `h:1`）和 `diffuse` 状态（`x:1/2,y:1/2`）；`g1` 只有 `only_heavy`（`h:1`）。两个组各有总质量 1 的合法状态。该 fixture 用于检验：联合选择时两个组都选 heavy 会共享 `h`，而 diffuse 状态提供另一种分散选择；既有独立后端枚举把该实例列为 `OPT=1`、实际峰值 1。这里的 `YES` 只属于该明确菜单输入，不等于所有带 heavy state 的实例都有同一性质。

## `near_two_single_state_no`

资源为 `h,a,b`。两个组各只有一个状态，分别使用 `h:16/17` 与自己的私有资源 `a:1/17`、`b:1/17`。两个状态必须同时取，`h` 上的质量叠加为 `32/17`；既有 root independent audit 把该实际矩阵枚举为 `OPT=33/17`、实际峰值 `33/17`。本源保存的是原始菜单 incidence，而非只保存一个近二数值，因而能明确看到“同一 heavy resource 的两组单状态冲突”机制。

## `zero_work_empty_and_duplicate_states`

资源为 `zero,unused`。`g0` 有两个空 incidence 状态 `empty`、`empty_copy` 和一个 `zero` incidence（`zero:0`）；`g1` 也有 `zero:0`。所有这些状态的总质量均为 0，且 `empty` 与 `empty_copy` 的身份仍由输入保留。既有有限审计把该 case 作为空/重复/零工作边界，实际峰值和最优值为 1；不得从“所有工作为零”把机器/selector 语义删掉或把重复状态当作输入错误。

## `rational_unequal_menus_and_bonuses`

资源为 `h,x,a,b`。`g0` 三态的质量分别为 `1/2`（`h:1/3,a:1/6`）、`2/5`（`x`）和 `1/11`（`h`）；`g1` 两态的质量分别为 `3/7`（`h:2/7,b:1/7`）和 `3/8`（`x`）。这是非均匀菜单/bonus 的精确有理输入，状态总质量不要求相等。独立 audit 把 9 个原始 jobs 的 768 个 assignment 全枚举，得到 OPT=1、实际峰值 1；本源独有的是菜单原件和每个 incidence 的精确分数。

## `aux_opt_zero_fallback`

资源只有 `h`，两组各只有 `h:1` 的单状态。辅助 MaxMin 量为 0 时，完整原矩阵仍要求两个状态在同一资源上，实际峰值为 2；该 case 是 `aux_opt_zero` fallback，而不是对 degree-two 算法的普遍失败证明。它确保辅助目标为零时实现有明确分支，不会把除零或空集合当成功。

独立 Fraction 结构检查确认五个 case 的资源 ID、组/状态 ID 均无重复冲突，每个 incidence 资源属于声明资源集，所有 `p` 非负有理，状态总质量与上述分类相符。既有 `degree_two_menu_joint` 证据还记录 832 个原始 assignment（32、16、12、768、4）及所有 eligibility/interval 检查；本页引用该审计结果，但校验脚本只对原始 JSON 做结构/有理复核，不把有限枚举扩大为一般算法定理。

与既有《笛卡尔分块一致性与二度菜单联合取整双源审查》比较，五个 case 的用途分开：`joint_bad_heavy_yes` 是有选择余量的 YES；`near_two_single_state_no` 是同 heavy 资源冲突的近二 NO；zero/duplicate case 约束边界处理；rational unequal case 测试非均匀 state；aux-zero case 约束辅助目标退化。它们共同支持的只是 degree-two 菜单对象的有限输入回归。既有正文中的 `OPT=2-V`、MaxMin balancing 和 bonus normalization 仍需使用其完整输入合同；本 JSON 不独立承担那些证明。

# 三源关系、处置与未决问题

三源共同要求保留输入合同与历史身份：

1. weighted fanout profile 的 `p/S1/S2/T/beta` 是加权扇出边界的一个小型 profile；它与五个 weighted menu 的 group/state/resource 结构共享有理资源语言，但前者不是后者的 state menu，也不承担 degree-two MaxMin 证明。
2. 五个 weighted menu 的有限 audit 与 fanout 的 `T(2-β)` 合同都属于受限 unrelated-machines 证据；它们都没有把未知 YES witness 搜索、一般 CONFIG 或一般近二硬度自动解决。
3. history README 提供历史路径和审查纪律，既不能为上述两个夹具增加新的数学量词，也不能把旧问题页的 OPEN/已完成措辞直接当成当前真值。

建议处置：`0c3bf6d24f1ba76ead00` 与 `b88c0af63e1cab4774d1` 均 `integrated` 到本页及 evidence 目录，接入既有扇出/二度菜单审查；`56adacf9717c2c0b7539` `retained` 为历史资源索引，原件保存在同一 evidence 目录。未决问题包括：一般 weighted fanout 的 witness 生成、跨模块容量与 CONFIG 不等式、degree>2 的菜单选择、辅助目标为零时的完整算法语义，以及旧历史材料与现行对象之间的逐源关系。任何这些问题都不能由本批三个小源单独关闭。
