# 2. 核心标准：每个段落和公式回答同一个问题

源文的基本准则是：论文中的每个段落、模块、公式和实验，都应该回答或支持论文要解决的核心问题。结构重构不是把模块重新排列，而是把模块放回“为什么需要它、它改变什么、证据是什么、边界在哪里”的链条。

主故事线通常是：

```text
真实需求 → 技术瓶颈 → 现有方法的限制 → 所需能力 → 提出框架 → 机制 → 验证 → 含义
```

方法型论文的局部版本是：

```text
核心问题 → 具体挑战 → 所需能力 → 模块 → 机制 → 证据 → 含义
```

源文明确反对“模块 A 介绍、模块 B 介绍、模块 C 介绍、最后做实验”的堆叠。推荐句式把每个模块从挑战引出：为处理某挑战，需要某能力，因此引入模块；在此基础上，下一个模块缓解剩余限制；最终模块支撑系统目标。该关系必须由源中的实际机制和证据支撑，不能凭写作顺序制造逻辑依赖。

转用于 UM 正文时，真实需求可以是待解决的调度/配置问题，技术瓶颈可以是全机整数解码、共同容量、位复杂度或量词缺口；但这些词只能从正式 `state/` 对象读取。结构方法本身不会将一个局部 LP、必要流或有限审计升级为算法或定理。

# 3. Diagnosis workflow：在重写句子前重建论证

源文要求按以下七步诊断：

1. 识别应用场景和核心研究问题；
2. 识别当前技术瓶颈或失败模式；
3. 写出既有方法在该瓶颈下做不到什么；
4. 由此定义所需能力，说明为什么提出的方法必要；
5. 把每个模块、公式、实验和结果映射到一个 claim；
6. 找出无证据主张、缺失转场、重复主张和模块堆叠段落；
7. 先产出修订后的故事线，再改写句子。

诊断输出应包含：核心问题、主线、章节问题、推荐重组和 claim/evidence 缺口。若输入是已有草稿，companion SKILL 的 verification mode 要求只报告偏差和位置，只有破坏硬规则时才就地修复；这样能避免“更好的重写”悄悄改变定理、数字、引用、数据集、指标或范围。

# 4. 段落功能标签

重写前给每段分配一个明确角色：

* 应用背景；
* 核心问题；
* 技术缺口；
* 方法动机；
* 模块机制；
* 公式定义；
* 理论分析；
* 实验设置；
* 结果观察；
* 结果解释；
* 限制；
* 实际含义；
* 过渡。

没有清楚功能的段落应合并、移动或重写。标签不是为了增加小标题，而是为了检查一个段落是否承担多个相互冲突的任务。特别是“结果观察”和“结果解释”要分开：表格/程序先报告输出，再说明为何与机制或主张有关；限制应命名其条件和影响。

这与已归档的反防御审计相容：必要的否定、失败逆命题和范围限制不能因为不够积极而删除；可以删除的是重复结论、假想读者免责声明和没有实际用途的提前预告。

# 5. Contribution framing：每项贡献都接到前文的 gap

源文用弱/强对比说明贡献写法：

弱写法是列“我们提出模块 A、模块 B、做实验”；强写法是说“提出解决具体缺口的能力 formulation、缓解具体失败模式的机制、在某条件下验证某 claim 的 targeted evaluation”。

每项贡献必须对应前文已经建立的挑战或缺口。不要让贡献列表突然出现读者此前没有看到的对象；不要以 `first`、`novel`、`unprecedented` 等优先权词替代相关工作证据。证据不完整时，使用“we focus on”“we develop”“we investigate”“we introduce a framework for”“under the evaluated conditions”等有边界的表达。

`archives/unrelated-machines/state/资料/贡献地图模板与主张证据风险边界--资料.md` 提供了与此相邻的结构化字段：`primary_claim`、`secondary_claims`、`non_claims`、`risks`、`reviewer_objections`。本源新增的是**叙事顺序与段落/章节的承接关系**；贡献地图新增的是主张—支持—风险的字段结构。二者都不创造数学结论。

# 6. 章节级要求

## 6.1 标题与摘要

标题应指出技术对象、关键能力和应用上下文，避免只列模块或作宽泛承诺。摘要按背景/问题、具体 gap 或 failure、方法与核心机制、实验或分析证据、受限含义五步组织。不要从一般领域重要性开头，也不要在没有证据时宣称广泛优越性。

## 6.2 引言

引言顺序是：真实需求、技术瓶颈、当前方法的限制、所需能力、提出方法、贡献和文章组织。末尾贡献不应让读者意外：它们要回答已在引言中建立的缺口。对 UM 来说，模型输入、目标、可行调度和当前开放义务必须在主线早期明确，不能等到贡献列表之后才补。

## 6.3 Related Work

源文建议按方法家族、假设或限制组织相关工作：家族 A 及其限制、家族 B 及其限制、最接近的工作、剩余缺口。不要按年份堆引用，也不要用模糊攻击语气。详细的文献选择、直接竞品覆盖和引文角色应交给 `problem-driven-literature-review`；argument reconstruction 只检查 Related Work 是否真正支撑主 gap 和贡献逻辑，不替它查全外部文献。

这条边界与 novelty-risk audit 一致：related-work 结构能指出主张所需的对照，但“没有找到文献”并不等于全球原创。仓库的来源映射和外部优先权资料仍需逐条保留版本、来源和未核范围。

## 6.4 Methodology

每个模块先从问题需求引入：为处理某挑战，需要某能力，因此模块提供某机制/作用。随后说明输入、输出、机制、与其他模块的关系、假设/限制以及它在全框架中的角色。标准 solver、LP、matching、Viterbi 或 pipeline 只有在源明确支持时才可称 contribution。

## 6.5 公式说明

公式前说明为什么需要它；公式后定义符号，并解释公式捕捉了什么机制。避免公式堆积，让读者看不出方程与方法的关系。UM 归档尤其应在公式旁给出对象、量词和费用/负载含义，不能只复制代数表达式。

## 6.6 理论与证明

理论段落必须写出假设、命题/定理含义、证明逻辑、结论、范围和限制。证明语气不能超出假设；必要条件、给定 oracle、有限参数、局部接口和完整算法要分开。源文强调“不要让证明听起来比假设更宽”，这与已有 UM 审查页的 sound FAIL、decoder、bit complexity 和有限 audit 边界相同。

## 6.7 实验

每个实验应验证一个 claim、模块、指标或部署要求，并写明 claim、数据/场景、baseline、指标、诊断价值和限制。不要只报告最终总精度；如果贡献依赖某个机制，应有消融或 targeted scenario。如果声称实时、鲁棒、安全或可靠性，应补 runtime、资源、失败案例和覆盖范围。

对于 UM，计算证据可以是精确整数/Fraction 重放、全状态证书、有限程序或反例搜索；它们必须标出输入、seed、算术、状态数、输出和未覆盖域，不能代替全称证明。

## 6.8 Results and Discussion

一个强结果段通常含五步：观察、比较、机制解释、与主张的关系、必要时的限制/条件。不要仅重复表格数字。结果解释也不能把相关性、预测、因果、决策或算法复杂度混在一句话里；每类 claim 需要自己的证据和范围。

## 6.9 Conclusion

结论回到核心问题，总结机制和证据，给出有边界的未来工作；不能引入从未评估的新应用、未证明的新算法或全局优先权。未解决缺口应保持为开放义务，而不是在结尾以更强措辞“补齐”。

# 7. Claim/evidence alignment 表

源文给出如下诊断表：

| 主张 | 所需证据 | 已有实验/证明 | 缺失证据 | 风险 |
| --- | --- | --- | --- | --- |
| … | … | … | … | … |

常见缺口包括：模块被称重要却没有消融；方法被称鲁棒但只测容易场景；实时/部署缺少运行时或资源分析；安全/可靠缺少失败案例；优越性没有危险 baseline。对数学写作，表中的“实验”应按真实证据类型替换为 proof、counterexample、exact replay、finite audit 或 literature source，并明确它们承担的结论方向。

该表与贡献地图的关系是：贡献地图记录主张、支持、非主张、风险和审查回应的结构；alignment 表记录每一主张需要什么证据、实际拥有多少、缺哪一块。只填地图而不补 evidence 不会提高 proof confidence。

# 8. 与 genre profiles、corpus 和 anti-defensive 资料的关系

已清洗的[数学写作文类剖面与主张责任边界](数学写作文类剖面与主张责任边界--资料.md)把 research article、theorem-proof、教材、统计、计算/实证和视觉伴随分别安排不同依赖顺序。argument reconstruction 与它的关系是：本源给跨文类的“问题→gap→机制→证据”主链，genre profiles 则约束每种文类的局部顺序和证据责任；不能把统计/视觉 profile 的模型规则直接迁移为 UM 定理。

[数学写作语料清单与测量边界](../资源/数学写作语料清单与测量边界--资源.md)保存 27 源语料、PDF/文本复现、词频和近读锚点，并明确这些是 corpus-bound measurements；它不能证明某种段落结构对所有论文都最优。argument reconstruction 使用它作为结构启发时，仍须回到当前 source 和数学证据。

[数学写作反防御功能审计与证据量词边界](数学写作反防御功能审计与证据量词边界--资料.md)负责 Keep/Rewrite/Compress/Delete/Flag 和数学否定保护。本源负责把段落、章节、模块和实验串成问题驱动故事；反防御审计负责不删假设、否定和失败边界。两者共同防止“结构简化”悄悄扩大定理范围。

# 9. 对不相关机器档案的安全用法

`archives/unrelated-machines/README.md` 与 `prompts/README.md` 规定正式数学条件以 state 正文为准；本源只能帮助整理已有对象，不得从“主线”词语推出新 claim。安全流程是：

1. 先从正式定义/定理/反例/审查中提取对象身份、输入域、量词、结论方向和证据路径；
2. 写出问题—瓶颈—缺口—能力—机制—证据—含义链；
3. 为每段和公式加功能标签，发现重复或无承重段后再移动；
4. 用 claim/evidence 表检查每个主张是否有足够证据，标记缺口；
5. 对已有草稿使用 verification mode，保留 TeX、数字、变量、引用、数据集、指标和结论，不用“重写”覆盖来源；
6. 最后做数学完整性比较，确认没有扩大定义域、加强量词、删除必要否定或把有限程序写成普遍结果。

如果对象仍是候选或未闭合，主线应诚实写为问题和开放义务，不应先包装成完成工作。若 related-work 或 novelty 事实不确定，回到对应审计/文献流程，而不是在 argument reconstruction 中补写。

# 10. 处置与未覆盖边界

本源处置为 `integrated` 资料/资源：原文 evidence 已保全，问题驱动主线、段落标签、贡献—缺口承接、章节级规则、公式/证明/实验证据责任、结果解释、alignment 表和 verification mode 边界均已归档。

它与 argument-reconstructor SKILL 的关系是：SKILL 规定何时使用、何时委派和如何验证；本参考文档给具体重构材料。它与 genre profiles、corpus、反防御、贡献地图和 novelty-risk audit 分工明确：不重复句子级审计、文类统计、主张字段或四层查新。

本条目不创建新的 UM 定理、算法、复杂度、gap、hardness、反例、外部新颖性、期刊定位或部署结论；也不把未读取的中文 companion、problem-driven-literature-review 或 paper-polisher 文件冒称本批已读。具体数学和外部文献仍须回到其各自正式对象、原始版本和可复核 evidence。
