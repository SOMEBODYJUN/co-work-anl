# 2. 决策序列：先确定限定的功能，再决定句子动作

当句子包含 caveat、hedge、contrast、clarification 或 negation 时，源文要求按同一顺序检查：

1. 先指出该句子实际修改的主张或对象。
2. 判断这段限定是否改变合法性、适用范围、证据类型、逻辑关系，或读者此刻必需的指引。
3. 把必要内容放回受影响的定理、公式、构造或观测旁边。
4. 若可从对象、可行类、输入域或贡献直接给出正向范围，就用正向范围表达。
5. 如果正向重写需要源文没有提供的目的、对象、编码、观测模式或适用范围，停止改写并标为 `Flag`，要求补足上下文。

这套顺序防止把“删掉防御性语气”误当作“删掉数学限定”。限定只有在功能测试表明它只是预先回答一个未指明的反对意见时才可删除；若它定义了可行域、量词、证据来源、逻辑否定或读者需要的对象翻译，就必须与主张相邻保留。

# 3. 功能分类与允许动作

| 功能 | 动作 | 对数学对象的含义 |
| --- | --- | --- |
| 数学假设 | `Keep` | 与定理、公式或构造放在一起，例如“可预测且平方可积的被积函数”；不能把定义域条件移到远处。 |
| 必要否定 | `Keep` | 保留“逆命题不成立”“局部鞅未必是鞅”“某变量不属于该滤过”等精确逻辑力量。 |
| 失败逆命题或反例 | `Keep` | 这是结果本身，不是防御性附注；其反例域和失败方向必须明确。 |
| 证据型限定 | `Keep` | 指出证据是定理、精确计算、有限枚举、模拟观测还是作者推导，并说明不确定性来源。 |
| 方法/数据限制 | `Keep` | 写明限制的来源、方向和作用一次；不要把同一个边界重复成多个免责声明。 |
| 有效概念对比 | `Keep` | 保留能推进充分/必要、定理/逆命题、一般/特殊情形等真实逻辑对立的 contrast。 |
| 可直接给出的正向范围 | `Rewrite` | 直接说定理适用于什么对象、类别或输入，而不是围绕“并非任意对象”组织段落。 |
| 冗余澄清 | `Compress` 或 `Delete` | 若相邻形式化语句已承担同一解释，不再重复。 |
| 假想读者免责声明 | `Delete` 或 `Rewrite` | 用随后真正的数学内容替代“读者不要误解”的预防性句子。 |
| 紧邻的形式翻译 | `Keep` | 当读者刚遇到对象、而该句把对象翻译成可用公式或编码时，应保留。 |
| 复述已结束的结论 | `Delete` | 改为定理、方程或图编号指针，避免在段末重述同一结论。 |
| 提前预告后文 | `Delete`，除非现在必须固定记号 | 不让后文内容取代当前段落要完成的数学任务。 |

分类是功能审计，不是按关键词机械删除。`does not claim`、`not intended to`、`this is not a proof`、`to be clear` 等只是 review signal；每次仍需判断该词组是否保护合法性、范围、证据或逻辑。

# 4. 正向范围与定义域量词

源文建议直接命名对象、类别、问题或贡献。例如与其写“定理不适用于任意被积函数”，不如写“定理适用于可预测且平方可积的被积函数”。这种重写有两个数学效果：

* 输入域、可行类或模型边界被明确写出，读者可看到量词落在哪里；
* 限定紧邻主张，避免把“只在某类对象上成立”误读为全类定理。

在不相关机器档案中，正向范围应具体落到真实模型：机器集合、任务资格集合、处理时间/权重域、整数或有理编码、阈值关系、完整分配义务和是否只讨论合法调度。若来源只证明某个 fixed-parameter、给定 support、有限状态或可重放实例，就用相同范围命名它，不能通过删掉“任意”“全部”或“仅”来扩大量词。

当上下文没有告诉我们要表达什么对象、哪种编码、哪一类观测或哪一个目的时，正向改写会制造新内容。此时 `Flag` 比猜测更安全：应把缺失的范围、编码、目的或量词补入来源/审查记录，再决定是 `Rewrite` 还是 `Keep`。

# 5. 图和模拟：先说编码，再说结论

源文把图/模拟语言分成两个工作：描述图上实际编码了什么，以及说明哪个定理支持什么结论。图的句子使用描述性动词，例如“每个标记记录一个输入–输出范数对”；数学主张由单独的定理或审查句承担。这样可以防止把一个图的形状误写成对全部输入的证明。

同样，模拟或有限程序只应陈述其实际观测。若误差在网格加密时约缩小四倍，正文可以写这个观察；若已有定理给出依概率收敛，再单独指出该定理的结论和图形提供的实验模式。若观测量超出所有可用定理，则使用“在这组实验中呈下降趋势，与某收敛结论一致”这样的弱措辞，并明确它是经验支持，不是证明。

限制也要命名来源和方向：例如区间代表 Monte Carlo 不确定性，网格间移动反映离散化误差。不要把“图不主张四个量有相同形状”作为图注的主要任务；应直接说明所画编码，再单独保留任何真正需要的数学限制。

转用于本仓库时，有限枚举、Fraction/整数审计、solver 输出、作者推导和正式证明要分层书写。程序成功运行只证明记录的输入、代码、断言和输出；它不会自动证明所有输入、渐近量词、外部复杂度或主目标。相反，定理、反例和 sound FAIL 的逻辑力量必须由其正式对象承载，不能被“实验上”“可能”“似乎”这类没有来源的不确定词削弱或扩大。

# 6. 数学否定保护

源文明确列举以下一类不能因“反防御”而删除的句子：逆命题不成立；局部鞅未必是鞅；布朗路径处处不可微；某变量不属于较早的滤过。共同特征是，否定词改变了定义、定理、反例、可行性条件、可测性或模型边界。

不相关机器档案中的同类句子包括：

* 一个配置 LP gap 只否定相应比较合同，不自动给出原问题 hardness；
* 某个 sound FAIL 只覆盖写明的输入域和阈值，不是对所有模型的无条件不可行性；
* 实际低峰值调度可以推出必要矩/流条件，但从该松弛的可行点反向得到完整整数 schedule 仍可能没有证明；
* 有限审计发现失败实例，不等于一般参数族或渐近定理；
* 一个局部 probe、给定 support 或 oracle 接口若未支付全机整数输出和位复杂度，不能冒充完整算法。

这些否定保留了对象间的逻辑分层。编辑可以压缩重复说明，但不能把“只证明必要性”“只覆盖有限审计”改成正面全称结论，也不能把“无反向声称”删到读者误以为已有 decoder。

# 7. 失败机制、模态和对比的功能测试

`May`、`might`、`could` 只有在量本身存在真实不确定性时才报告不确定性。计算/经验写作可用它们说明抽样或观测的不确定性；如果来源已经把结论定死，再用模态词会降低证据等级并模糊责任。`However`、`although`、`whereas`、`in contrast` 在确有充分/必要、一般/特殊、定理/逆命题的对立时应保留；只为装饰转折而写的 contrast 可删。

审查模式应逐条报告：

1. 原文段落或句子；
2. 当前句子的功能；
3. 限定是否数学必需；
4. 动作 `Keep`、`Rewrite`、`Compress`、`Delete` 或 `Flag`；
5. 一句理由。

修订模式则先执行这些决定，再做数学完整性比较：检查定义域、量词、假设、结论方向、证据等级、反例和复杂度是否与修改前一致。这个“先审计、后重写、再完整性比较”的顺序是失败机制的核心防护：它避免语言优化把必要假设删除，或把有限观测升级成全称结论。

# 8. 对当前 UM 存档的操作规则

与 `archives/unrelated-machines/README.md` 的状态定位和 `prompts/README.md` 的“数学条件以正式正文为准”一致，本资料的使用方式如下：

* 正式对象开头先写对象身份、输入域、量词和要证明/反驳的关系；方法/来源/证据放在其承担的位置。
* 来源、作者推导、独立重构、有限程序、精确证书和最终定理分开标注；不要用一个来源表或运行日志代替证明。
* 图表和模拟先说编码、输入、输出和观测；随后另写定理或审查结论，并把强度归于对应证据。
* 反例、failed converse、不可行性条件、模型边界和“只作必要条件”的句子保留其否定力量。
* 只在来源已经给出正向对象/类别/范围时做正向重写；缺少目的、对象、编码、观测或量词就 `Flag`。
* 对有限实验或局部检查写清规模、种子/程序、算术和未覆盖域；不要把“运行通过”写成一般定理。
* 章节结束时若结论已由定理、公式或图编号承载，删除重复结论，把段落收在当前数学任务完成处。

这些规则帮助现有审查页保持定义域、soundness、decoder、bit complexity 和证据等级的边界。它们不改变任何既有数学对象，也不要求所有正式正文采用同一种风格；功能和可验证性优先于词频。
