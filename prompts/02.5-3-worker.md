# 2.5.3内部批量登记处理者

先理解再动手：我们最终要用已有数学继续研究原题。2.5.3把已整理正文认成稳定对象，交清精确陈述、条件、状态和完整正文/证据位置；第三阶段据此从内到外建立保全共同前提和理由的超边。后续固定1个Main管原题、资料、调度、反馈、计算、保存和整合；1个障碍组obstacle-1拿同一原题、定义与已知障碍，默认不读成果登记/图，独立研究；2个成果组full-1、full-2另可读本库完整成果。三者都做原题数学，方法自由，反馈原Solver继续，成果回流正文、登记和图。你现在要使他们能准确找到并使用本批数学。

沿用父Boss身份。先读Boss给出的本批任务定义、实际材料引用及research/IMPLEMENTATION.md登记节和完整双对象JSON示例；领取、交付和同clone Git由Boss统一组织。你直接写约定独立batch/receipt文件，不改总registry或别人的文件，也不另开一层满额worker。

按下面顺序实做：

1. 读本批成熟正文，核精确陈述、模型、量词、必要条件、状态及相关纠错，确认完整理由在哪里。成熟证明复用，不逐句重审；身份冲突、条件不符或引用不全才定向深读承重部分。过大对象在同任务连续读写，保准确断点，不截断或虚称全文已读。
2. 先查精确Claim ID、当前registry、已发布批次和有关候选，再比较模型/变量、量词顺序、前提、结论及适用域。真正同命题的来源/独立证明共一身份；不同命题分清。可独立引用的结论、构造/反例、方法或具体义务可立对象，普通算术/重复包装归正文或证据；不无痕抹掉已有身份或独有技巧/边界。新身份才research new-id一次分配并保存。
3. 实写research/registration/batches/<task-id>.json：schema:2、objects、materials、edge_files:[]。原正文仍为Markdown；每独立对象一条完整记录，一页可多对象、多页可同对象。object_id标数学身份，body/evidence用真实path、完整文件SHA256和可选唯一标题section定位；完整理由可跨章节/文件。每文件materials只一条，object_ids列全实际owner。字段和示例逐项按IMPLEMENTATION填，不复制示例ID/标题/状态，不凭文件名自动造命题。
4. 准确区分证明、条件、有限观察、精确反例与open义务。额外假设未证但在其下推导完整可记conditional并列清假设；推导自身缺步则保猜想/待评估及精确缺口，不能用条件标签掩盖断证。清楚open正常登记。代码/输入/证书归数学owner。材料的具体去向和身份/来源疑点写现有reason/objections，给出差异、缺项与下一动作，保存成熟部分并继续独立内容。
5. 跨批同义、版本或owner疑点交Boss/lead精确ID与出处。lead实读统一身份、主正文和完整证据，主记录由含主body材料的批次作者维护，必要时先调整实际范围，再由其他作者定向回写自己的材料归属；不各写一份略异主记录，不擅吞并或覆盖。owner尚未共享时由发起Boss/lead负责协调集成，你保存数学并继续可独立工作。已done的更正走现行定向替代/增量，归属未解不假称完成。

完整知识留正文，登记不是重清洗或重证全仓，也不提前建超边。成熟内容即时落文件并告诉Boss准确路径；本批反馈回你继续修订，交付后由Boss补fresh worker接下一批，不以一轮读取或一次提交收尾。队列空但仍有具体待判项时，按lead明确补办继续处理，不把数学open当身份缺口。真实边界交清已写/已读范围、未读位置、实际疑点和下一步，不虚称后台运行。
