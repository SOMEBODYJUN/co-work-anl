# 2.5.3：批量登记数学对象

## 第一步：先理解我们的工作，再开始登记

你和每个worker先读懂这些安排，再直接工作。前面的整理已经形成数学正文；现在要让后续数学研究Agent准确找到、理解并使用这些积累，继续解决用户的原题。

2.5.3负责认清已有数学对象、沿用稳定身份，标明精确陈述、条件、状态及正文/证据位置。第三阶段再从对象内部、同子档、同档到跨档，读出哪些前提共同承重、哪些结果可迁移、哪些反例否定哪条陈述，写成保留完整理由的超边。登记告诉后人“有什么”，超边告诉后人“怎样一起使用”。

后续研究固定1个Main＋3个Solver：Main负责原题、资料、调度、反馈、必要计算、保存和整合；1个障碍组obstacle-1拿同一原题、完整定义和已知失败边界，默认不读成果登记/图，独立研究原题；2个成果组full-1、full-2还可使用本库正文、登记、完整超边及证据。三者都实质研究同一原题，方法自由，反馈交原Solver接着做；有价值的新成果再回流正文、登记和图。你现在准备的身份、条件和证据必须使这个团队能继续数学推导。

## 每批实际怎样登记

1. **读清本批内容。** 先核精确陈述、模型、量词、必要条件和真实数学状态，确认body/evidence覆盖完整理由的位置，并看相关现行纠错。成熟证明可复用，不逐句重审；身份冲突、条件对不上或引用缺失时，定向深读对应承重论证。完整知识留在正文，登记不能把证明缩成一句摘要。
2. **先对照，再定身份和粒度。** 查原文精确Claim ID、当前registry、已发布批次及正在协作的相关候选，读必要相关正文；无registry时也先查原文身份和相关已写成果。比较模型/变量对应、量词顺序、前提、结论和适用域。同一精确命题的多份来源/独立证明归同一身份并保留证据；不同模型、量词、条件或结论不能只凭同名、新旧或强弱吞并。可独立引用的结论、构造/反例、方法和明确义务可立对象；常规代入、普通算术和重复包装留在相应正文/证据中。已有身份的合并或退役须交清准确去向；弱结论的独有技巧和失败边界仍须保留。
3. **实写JSON。** 每批写research/registration/batches/<task-id>.json及对应receipt；顶层schema:2、objects、materials、edge_files:[]。一页多对象在objects各写一条，多页同对象共用身份；原Markdown不必拆。object_id是数学身份，body/evidence用path＋完整文件SHA256＋可选真实唯一标题section定位；证明和必要定义可跨多条引用。同文件在materials只记一条，object_ids列全该文件实际承载的对象。字段全集、引用规则和完整模板按IMPLEMENTATION实际填写，新身份才用research new-id分配一次并保存。识别、比较和填写由你完成，程序只核结构、字节和归属。
4. **交清状态与材料去向。** 已证、条件、猜想、精确反例、有限观察和明确open义务按实况区分。额外假设未证但在其下推导完整可记conditional并列清假设；推导本身缺步则保猜想/待评估和精确缺口，不能用条件标签掩盖断证。open不等于尚未登记，也不要求先解完。代码、输入、证书归数学owner，普通数值和日志不造节点。每份材料给出对象、附件、排除或具体待判去向；发现身份/来源/解释疑点，在现有reason/objections写清具体差异、缺什么及下一动作，保存已清楚部分并继续独立工作，不把整包停在一句“待处理”。
5. **跨批同义和冲突由lead实读决定。** 给出相关ID、陈述差异和承重出处。lead比较后统一身份、主正文和完整证据，主记录由实际分配到主body材料的批次作者维护，必要时先调整批次范围；其他作者回写自己的材料归属，不各复制一份略异主记录。尚未共享的owner由当前发起Boss/lead负责协调集成后接续交付，不能发条消息就丢给别人。未交付草稿直接定向改，已done按现行定向替代/增量修正，不覆盖旧批资产。compose不会替你判断数学同义。归属未解时保全数学、继续其它可独立工作，不抢他人范围或假称完成。

## 持续并行、保存与出口

先恢复本人未完，再按当前实际空位claim-next --count N批领阅读包。默认gpt-6.1-sol、reasoning_effort=ultra，以用户明确配置为准，用满实际可用并发；Boss和worker都做数学，不设常驻汇报/审批岗位。worker读prompts/02.5-3-worker.md，直接写约定独立文件；同clone Git由Boss串行组织。只给已确认pushed且当前owner仍为本Boss的任务派工，不逐材料认领或预占以后批次。

```sh
python work.py registration-task claim-next --count <当前实际空位>
python work.py checkpoint <本次明确产物路径> -m 'Publish registration batches'
python work.py registration-task done --record-file <本次成熟批次的ready.json>
```

成熟几个就保存、确认pushed并批交几个，不等一整轮。ready和receipt格式按IMPLEMENTATION。批内反馈交原worker修订；一包交付后立即补fork_turns:none的新fresh worker接下一包，给Boss号、clone绝对路径、本批任务路径、内部词及必要数学边界。明确继承旧worker时按已用或未知历史预算，不把旧包当空历史。

lead边收边读，核每份材料中有研究作用的独立内容都有准确去向、无误合并/重复身份、正文证据可读，再collect→保全并sync→compose/register→checkpoint唯一research/registry.json；具体命令和增量规则查IMPLEMENTATION。新材料或改正文按现有冻结/增量规则接入，不重启全仓清洗。第三阶段或研究中的补登记，由发起Boss/lead携具体对象、出处和理由协调本run当前lead实际完成；无主显式接任，消息发出不算交付。

**持续循环：恢复未完→补实际空位→读写整批→成熟即保存/pushed、批交→lead整合→接下一批。** 只要本范围还有未处置材料、身份/来源疑点或未整合交付，就继续，不以一轮、一次提交或暂时队列空收尾。队列空但final仍有needs-decision时，lead把具体疑点定向补办给原作者或实际空位；已done批按既有替代规则修正。无主须显式接任lead，不能只等待别人上线。

全仓本轮输入都有准确去向、稳定身份与完整证据/owner，跨批冲突已解且已推送后，用research registration-check --final独立核登记。字段通过不替代数学判断，登记出口不要求先有图或解完开放题；随后交第三阶段使用当前registry、正文与证据。本轮准确出口已pushed并交清baseline、总表及下次增量入口后，lead也用registration-task lead handoff --reason <准确出口与接续位置>交出集成位，供后续合法接任；不在一包完成就交出整轮职责。真实暂停用registration-task handoff --all --reason <实际原因>交草稿位置、共享情况和下一步，lead另交接；认证失败保全local-only并停止新认领。准确区分pushed、仅本地和未完，不虚称后台继续。
