# 2.5.3：批量登记数学对象

## 第一步：先理解我们的工作，再开始登记

**你先读懂下面的安排，再开始认领和登记。每个子agent也要先读懂，再处理自己的批次。理解后直接继续实际工作。**

**我们最后要做的是数学研究。** 前面已经把数学资料整理成正文。接下来要让数学研究Agent真正用上这些积累，围绕用户给出的原题继续证明、找构造、找精确反例，或者推进卡住的问题。登记和超边都是为这个用途准备的。各存档研究各自的问题，模型、条件和量词要分清。

**现在2.5.3要做的是给现有数学对象登记身份和位置。** 读已经整理好的材料，辨认其中的定义、结论、反例、方法和明确的未解问题，沿用或分配稳定ID，记清它准确说什么、适用什么条件、正文和完整证明/必要证据在哪里、是什么数学状态。同一对象来自多份材料时归到同一身份；同页不同命题要分清。这样做，是为了让后面建超边和研究时能准确找到、引用这些数学。当前直接批量完成登记，不重新清洗或重证全部旧成果，也不提前建边。

**第三阶段要做的是读出数学对象之间真正的关系，建立超边。** 登记说明“有哪些数学”；超边进一步说明“这些数学怎样一起使用”。先看对象内部的承重论证，再看同子档、同档，最后看跨档联系。例如A和B共同才能推出C，就保留这一整组前提、条件和证明，不能写成A单独就能推出C。反例要指明反驳的准确命题，迁移要说明模型和条件如何对应。这样后面的研究Agent才能沿已有推导继续做数学，而不只是找到几个看似相关的标题。

**第三阶段之后，研究团队按1个Main＋3个Solver设计。** Main负责拿准原题、选择资料、调度、反馈、必要计算、保存和整合成果。三个Solver都研究同一个精确原题，数学方法自由：

- 1个障碍组Solver（obstacle-1）：拿原题、完整定义和已知障碍/失败边界，默认不读成果登记和超边，从原题出发独立研究；它同样要做证明、构造和实质推进。
- 2个成果组Solver（full-1、full-2）：拿同一原题，还可以查本仓库的登记、正文、完整超边和必要证据，利用已有积累继续推进。

Main持续接收成果、整合并把具体反馈交回原Solver接着做；三个Solver持续推进到原题准确闭合或真实运行边界。有价值的新成果再写回正文，定向更新登记和超边，供后续研究使用。

**你现在做2.5.3，就是为这个研究团队把已有数学认清、编号并标好准确位置。** 按这个目的判断登记粒度、重复、矛盾和取舍：保留准确且有研究作用的内容，合并重复包装；根据原文、模型、量词、条件和论证处理冲突，不能仅凭新旧或结论强弱覆盖独有内容。把判断落实在现有字段和正文/证据定位中，整批做完后继续下一批。

本次身份：Boss【用户指定唯一编号】。未给先问，不自选、不借号；内部worker沿用父Boss。任务是把已整理数学登记成稳定对象与正文/证据入口，复用成熟正文，不重做清洗、证明或超边。

## 实际登记写什么：一份正文可以对应多个对象

**数学正文继续留在原Markdown；你实际要写的是JSON登记文件。** 每批写`research/registration/batches/<task-id>.json`，顶层为`schema:2`、`objects`数组、`materials`数组和空`edge_files`数组。一个独立数学对象在`objects`里占一条记录，一份文件可以对应多条对象记录，不要求拆成多个Markdown。lead随后把各批JSON合入`research/registry.json`。

实读材料后，逐对象填写`object_id`、`version`、`title`、`kind`、`truth_status`、`model`、`statement`、`quantifiers`、`assumptions`、`scope`、`objections`、`body`、`evidence`、`sources`。有精确旧Claim ID就沿用，新对象才分配ID；ID标识数学对象，文件名和文件hash不能代替它。`version`从1开始，对已有记录的修改按现行版本规则递增。

`body`是正文引用：`path`写仓库相对路径，`sha256`用完整文件原始字节实际计算的64位SHA256，`section`可选，填写原文中精确且唯一的Markdown标题文字（不含开头的`#`）。程序从该标题读到下一个同级或更高级标题之前。比如一篇文章已有两个包含各自完整陈述与证明的章节：

| 对象记录 | body.path | body.sha256 | body.section |
| --- | --- | --- | --- |
| EXAMPLE-A | 同一篇正文.md | 同一个实际文件SHA256 | 命题A与证明 |
| EXAMPLE-B | 同一篇正文.md | 同一个实际文件SHA256 | 命题B与证明 |

上表示意值须替换为实际值。两个对象共用同一文件与hash，靠各自稳定ID、精确陈述和对应章节区分。若完整证明、必要定义或证据还在其它章节/文件，就在`evidence`数组补其`path/sha256/section`引用，不能只指向一行结论。若正文没有合适的唯一标题，可省略`section`引用全文并用精确陈述辨认对象；不能编造标题或自造行号/chunk字段，必要定位疑点交Boss定向解决。

同一份文件在`materials`中只写一条，`object_ids`列出它实际承载的全部对象；上例为`["EXAMPLE-A","EXAMPLE-B"]`。程序会核对每个对象确实引用了这份材料。`sources`记录实际可追溯来源标识，不能替代正文/证据的精确引用。完整可照写的双对象JSON在`research/IMPLEMENTATION.md`的“一份正文登记两个对象的完整格式”一节；开始写批次前先读该节并替换全部示例值。对象的识别和填写由你与worker实读完成，程序负责校字段、字节绑定和归属，不会按文件名自动替你识别命题。第三阶段的超边端点使用`object_id`，因此同篇文章里的不同对象可以分别连接。

## 启动与持续执行

自动定位work.py、仓库外凭据和独立clone，先核目录、Git状态、remote及远端并保全已有工作。原对话恢复原clone、身份及未完批次。附件若在start --help中没有--workflow-run/curator，只借其认证能力恢复https://github.com/SOMEBODYJUN/co-work-anl.git的rebuild/research-v2，再用clone根程序；不拿旧start登记或覆盖仓库文件。已有clone若绑定旧阶段或另一对话，保留并另建本阶段独立clone；同阶段同对话才恢复原clone。

```sh
python <当前work.py> --repo <独立clone> start --actor BossN --role curator --save repository-cleanup --branch rebuild/research-v2 --workflow-run p25-register-v2 --token-file <仓库外凭据>
cd <独立clone>
python work.py doctor
```

N为用户编号，此后只用该clone根work.py。任务/身份在research/operations/p25-register-v2，公屏wcg/board-registration-v2。先读AGENTS.md、research/IMPLEMENTATION.md、research/PHASE3_READINESS.md及实际整理出口；内部处理者自行读prompts/02.5-3-worker.md，用户不用另配文件。

先registration-task list --owner self恢复本人未完，再lead show和实际公屏。已有lead接其任务，无lead时lead claim，CAS成功者承担集成且做实质登记。Boss与全部worker都读数学、比较、写文件；同clone Git由Boss串行，worker直接处理所分批次。默认gpt-6.1-sol、reasoning_effort=ultra，以用户明确配置为准，尽快用满实际并发，不设置常驻汇报/审批者。

持续循环：本人未完→填空位→读写整批→成熟即保存/pushed→批量done→接下一批→lead持续整合。批内反馈给原worker修订；本批交付后立即补fork_turns:none的新fresh worker，给明确Boss号、clone绝对路径、该批任务路径、内部词和必要全局边界，Boss身份不变。明确继承/复用旧worker时扣其已用或未知历史预留，不能把上批几百K当0。范围未准确处理完就继续，不以一轮、一次提交、暂时队列空或自设预算结束；无可领项就给lead具体补位范围。

## 批量计划与交付

仅lead在本run无已发布baseline时初始化；其他人复用，不反复冻结：

```sh
python work.py research prepare-inputs --scope repository --coverage-note '第二步当前正式材料及必要附件' --output research/registration/inputs.json
python work.py checkpoint research/registration/inputs.json -m 'Publish actual registration inputs'
python work.py research freeze --inputs-file research/registration/inputs.json
python work.py checkpoint research/registration/baseline.json -m 'Publish registration baseline'
python work.py sync
python work.py research batches-draft --baseline research/registration/baseline.json --output research/registration/tasks.json
python work.py registration-task plan --record-file research/registration/tasks.json
```

输入绑定真实Git正文版本；稀疏缺页先恢复，局部用--scope partial及重复--path；未提交的正文先保存，改字节另冻新baseline，不覆盖旧输入。

一个task就是一个按预算打包的材料阅读包，数量上限默认200而非必须凑200。当前正式正文实测常见约35–45份/包，短材料可100以上，实际以草稿为准。Boss一次claim-next --count 6可取6包、合约200份分给现有6个worker；不是每个worker再各spawn6个。每批只一次claim、一次done，绝不逐材料远端认领。已有计划先恢复，不重复plan已发布批次；确有新输入或尚无本轮计划才draft。planner默认跳过已准确处置且SHA未变的材料，只把新版本/未决材料入批；显式重审才用--include-registered。sync用于本地正文/registry一致；绑定阶段planner另读最新轻量队列metadata排重，同名候选直接刷新，已发布任务不覆盖。planner直接产现有队列能读的任务数组；lead按实际数学关联修订这份草稿，不另填第二套全仓owner表。材料共享阅读，写路径独立。若回执tasks=0，不执行空表plan；恢复现有在领/已完成批次并整合，以实际final判定是否完成，不把空队列当完成。

默认以所用Sol在Work/Codex的官方500K窗口规划：40%预留给其它上下文/推导/工具/输出，正文/元数据初值300K、总预留200K；显式改窗口时同比缩放，已用历史另扣，可调；这不是系统实报剩余。看context_plan中的字符、字节、估计token与方法，重复引用按实际区间去重，不把字符当token或填满窗口。单件超预算时保同task，按明确章节连续读写，不为每pass开新认领；保完整证明位置与准确断点，不截断或冒称已读；其它模型不套500K。

```sh
python work.py registration-task claim-next --count <当前实际worker空位数>
python work.py registration-task done --record-file research/registration/ready.json
```

count是任务数，不是材料数。只给当前owner仍为本Boss且已确认pushed的任务派worker；领取回执给短摘要及任务路径，worker按路径读本批完整定义，不把全表塞进Boss上下文。每批直接写research/registration/batches/<task-id>.json和对应receipt；schema:2，objects/materials齐全、edge_files:[]，receipt含batch_file及assets精确path/SHA。

成熟成果只列本次明确产物路径，合并一次checkpoint确认pushed，Boss自动把当前可交条目写成ready.json数组`[{"task_id":"已完成批次ID","receipt_file":"实际收据路径"}]`，一次done批交；单批done TASK --receipt-file仍可用。成熟几个交几个，不等凑齐全部worker。一次CAS核全部条目，错误不部分发布；未知回执保原输入/request核远端。ready是当次命令输入，不是第二账本；仅确认pushed后删临时ready，失败保原输入。用户已有明确固定owner安排则遵守，可选assignments-draft/check只辅助排批，不接管队列。

## 数学身份、集成与结束

本步先核成熟正文的精确陈述、模型量词、必要条件、来源与owner，定位现有完整body/evidence；没有新疑点不重新逐句验完已整理证明，有疑点才深读承重论证，并如实记录已读范围，不冒称全文复读。一页多对象、多页同对象，精确Claim稳定ID优先，容器页ID不吞不同命题；新身份才new-id一次分配。保model、statement、quantifiers、assumptions、scope、truth_status、objections、来源及完整body/evidence。模型、量词、域或结论不同不因同名合并，同对象实质变更增version。完整知识留正文，不为编号切碎或重写。

登记定义、模型、命题、有效反例、构造、可复用方法、算法保证、猜想、障碍与开放义务。普通算术、单次数值、程序、日志和PASS不造节点；必要输入/代码/证书归数学owner。精确有限反例有证明可proved，扫描为finite；被否桥与原题分开。清楚open正常登记，needs-decision只保身份/来源/路由疑点，不要求先解完开放问题。

lead持续collect --baseline <本轮baseline>只看短摘要，保全后sync，以baseline精确引用+workflow_run:p25-register-v2写短manifest自动收已done批次；需直接导出机器manifest才用collect --baseline <路径> --full并保存JSON，不把全量表打印进Boss上下文。research compose生成research/registration/proposed.json，消解冲突后register到唯一research/registry.json并checkpoint，不等全部人结束。后续用mode:incremental及base_registry精确引用保旧对象、材料与边；新baseline不重收旧批，同baseline改已done批才supersedes并明确旧资产去向。具体字段在IMPLEMENTATION。

全部真实输入有准确去向、稳定身份、完整证据/owner且冲突已处理后，research registration-check --final独立验登记，不要求图，字段通过不替数学判断。过期未领/已交接任务由lead withdraw，claim-next跳过并报告待重派项。

全范围准确处理完才交出口。真实暂停registration-task handoff --all --reason <实际原因>保草稿/共享情况/下一步；lead另交接。真实运行边界保本地及原请求，准确区分pushed、仅本地与未完，不虚称后台继续。随后第三阶段用prompts/03-map.md。
