# 第二阶段半：研究资产登记与 Work 图编排

~~~text
本阶段不是重新清洗来源，也不是把多个数学对象强行合并；它把第二阶段已经形成的细粒度 Markdown 对象登记成可供研究 Agent 调用的 Research Packet。

底层来源仍逐源保留哈希、处置和版本关系。每个数学对象仍保留自己的 Markdown；一源多对象、多源同对象只在登记表中表达关系，不能为了减少文件数静默改写正文。

## 研究包登记

每个 packet 必须绑定一个 problem_id、一个或多个 object_id、实际正文路径、来源和证据。登记内容至少包括：

- 当前问题、精确定义、模型身份、量词和适用范围；
- 已知结论及其 claim_type（定义、定理、条件结果、反例、障碍、有限检查、猜想）；
- 开放边界、失败路线和不能继承的结论；
- 证据文件、运行入口、已知命令或尚缺复现条件；
- 相关对象和局部关系；
- 下一批可检验问题；
- 三种上下文视图：full、boundary、blind。

JSON 只负责路由、登记和状态；数学推导、证明、反例和限制写回独立 Markdown。JSON 通过 `research/schemas/` 校验，Markdown 是人和 Agent 阅读的主要正文。

## 六个 subagent 的默认编排

Research Boss 保留整合权，六个 subagent 只提交结构化结果，不直接改写其他 Agent 的结论。

- continuation 模式：4 个 boundary + 2 个 blind。已有路线较清楚，需要高效推进时使用。
- hard-open 模式：2 个 boundary + 4 个 blind。问题难、地图可能有锚定风险时使用。

boundary Agent 读取 packet、相关对象、局部图、证据和开放边界；不得把局部关系扩写成全仓定理。

blind Agent 只读取问题定义、严格约束和允许读取的原始材料，不读取已有结论和超图边；它的职责是独立提出路线、特例、反例或障碍。

默认不启动常驻 verifier 或 adversary。只有某个具体候选需要复现、反例搜索或形式检查时，Research Boss 才临时把一个空位改成对应任务。

## Work 图节点

推荐的轻量节点顺序：

`packet_select → boundary_fanout / blind_fanout → result_collect → boss_synthesis → writeback_gate`

节点之间传 JSON 结果和对象 ID，不传整仓全文。需要正文时，Agent 通过对象路径和 evidence_refs 按需读取。Work 侧不能执行 CLI 时，由受控的 read/write/reproduce 工具节点完成对应动作；工具不可用就登记 blocked，不能口头假装完成。

## 结果要求

每个 Agent 只返回一个 `research-result` 对象，并说明：

- 采用的 context_profile 和路线；
- 假设、目标、claim_type 和当前状态；
- 依赖的 object/source/evidence refs；
- 新想法、与已有对象的关系或明确重复；
- 下一步检验动作和失败边界；
- 是否请求一次性复核。

Research Boss 合并的是结果和路线，不直接合并数学正文。只有在对象身份、量词、来源、证据和适用范围一致时，才把结果登记到已有对象；否则新建对象、更新边或记录失败路线。

## 登记门槛

- packet 没有完整模型和边界，不能进入 blind 或 boundary fan-out；
- 只有“读过/相关/可能成立”而无具体 refs 的结果只能是 lead；
- 新 claim 先登记 proposed/conditional/blocked，不能直接写 accepted；
- 写回前必须保留原始 Agent 输出、packet_id、result_id 和提交号；
- 研究图可以分支、暂停、剪枝和恢复，失败路线保留，不能因为一次运行结束就判定问题完成。
~~~
