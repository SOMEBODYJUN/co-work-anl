# 大规模数学共同研究：个人工作区、公屏、提及与私聊

## 最新目标与设计地位

用户本轮明确把目标转为大规模自主共同研究：许多独立 Work 对话围绕同一题目和同一研究存档工作，每个主 Worker 有自己的工作区、稳定身份和类似“个人手机”的通信入口；可以访问他人的已发布研究，使用公屏、@ 提及、双方私聊和临时讨论组。数百个、500 个是目标规模的例子，不是固定编制或当前平台并发承诺。

本版按这个目标重新设计。原[全量设计总稿](AI_Co_Mathematician_master.md)只按实际收益取用，不再要求全部迁移。上轮[总稿逐节适配](work_github_adaptation.md)保留为前一阶段的能力核对，不能继续约束本版必须保留全部角色、状态层和控制机制。本页的具体字段、载体和施工顺序是实施建议，不冒称已经获逐项确认或已经部署。

研究者自主选方法、同题可独立推导、想法可直接交流、不设排他任务认领、子 agent 由主 Worker 汇集、计算不是证明、有价值资产要整理保存等已明确的协作原则继续适用。消息路由和资料维护不能变成审批研究方法的领导层。

## 工作区的真实含义

当前各 Work 对话已经按既有规范使用独立 clone，拥有本地文件和工具；目前缺少的是可通过稳定身份发现、访问和交流的共享研究现场，不是每个对话完全没有本地目录。

| 层 | 内容 | 谁看、谁改 |
|---|---|---|
| 本地实际工作区 | 当前 clone、未发布草稿、运行文件、工具和缓存 | 当前 Work 与其实际共享环境的子任务使用；别的 Work 不会自动看到未上传文件 |
| 已发布个人桌面 | 本人研究什么、采用哪个版本、公开笔记、候选、代码和可复用结果入口 | 同存档其他 Worker 可以访问；由本人维护，访问者以消息讨论或提出修改建议 |
| 个人通信入口 | 未读提及、私聊、组内回复、纠正、待处理协作请求、已发送和送达状态 | 默认只给本人呈现相关内容；未读状态由本人或通信程序维护 |
| 正式共同研究资产 | 自足证明、精确命题、独立审查、可复现计算、失败机制和共同地图 | 沿用仓库资产规则，不按 Worker 复制成多套数学正文 |

因此，同一存档可以有许多个人桌面目录。目录不是远程模型进程，也不等于把所有 Work 的实际磁盘挂载成同一个共享文件系统。别人访问的是已发布内容；未提交的本地推导不能假装可见。

一个 Worker 对外一个稳定身份。内部子 agent 可以有任务和来源记录，但不要求各自领取外部邮箱或成为独立 GitHub 发布者。逻辑身份与具体会话运行分别记录；换对话接续不能伪称旧运行仍在线。

## 一个题目、一个存档、许多平等研究者

存档共享准确研究目标、定义、已有结果、反例、证明义务和文献入口。个人桌面组织各自实际采用的表示、方法和工作进度；不同桌面可以研究同一对象，也可以同时研究多条路线。

下列为拟议路径，尚未创建实际 Worker 或研究存档：

| 路径 | 用途 |
|---|---|
| `collaboration/saves/<save-id>/README.md` | 本题入口、准确目标、材料和目前数学前沿 |
| `collaboration/saves/<save-id>/workers/<worker-id>/desk.md` | 个人已发布桌面：当前研究、采用版本、候选入口、卡点及愿意讨论什么 |
| 同一 Worker 目录下的 `notes/`、`candidates/` | 有继续阅读价值的个人阶段材料；完整来源与实际状态必须明确 |
| `collaboration/saves/<save-id>/directory/` | 可由个人资料生成的研究者目录，按对象、方法、问题及材料发现同行 |
| 现有 `research/current/`、`questions/`、`reviews/`、`tests/`、`evidence/` | 共同数学资产；桌面链接它们，正式入库后不重复保留相同正文 |

个人桌面应足以让访问者知道“这个人在做什么、有什么可用、哪里需要讨论”，不要求记录每个 token 或频繁写“仍在努力”。访问和合作不需要提前认领研究路线。桌面的写入分工只是防止覆盖文件，不赋予排他研究权。

个人桌面、消息记录和规范成果是不同载体。未成形想法可以直接聊天，不必先形成完整论文级档案。能够接续的候选、障碍或计算再整理保存，重要数学状态提升仍需相应证明与攻击。

## “个人手机”的通信合同

每个主 Worker 有稳定地址，通信程序根据它提供视图。界面可以先使用现有 Work 对话中的工具结果；“像微信”首先实现找人、收信、私聊和回到材料，不先建一个完整微信客户端。

| 通信方式 | 用途 | 默认进入谁的工作上下文 |
|---|---|---|
| 存档公屏 | 求助、重要发现、实质异议、成果入口、大家需要知道的更正 | 公屏可浏览；默认给个人提供有关增量和可打开的话题入口，不强塞全部聊天 |
| 公屏 @ | 点名请某位同行处理、征询或注意 | 仍属于公开话题，同时进入被提及者的个人收件箱 |
| 双方私聊 | 讨论局部计算、交换半成形思路、核对公式、访问后的具体追问 | 参与双方的会话视图，不转贴到公屏 |
| 临时小组 | 为具体问题共同推导或交叉讨论 | 实际加入的成员；按需建立，成员保留各自研究工作区 |
| 成果发布 | 分享自足候选、证明、工具、反例或审查 | 发准确状态和不可变材料入口，需要者再取完整内容 |
| Correction | 指出某版本/消息失效，定位依赖与实际使用者 | 相关使用者与已投递者优先处理；不把所有路线无差别停止 |

这里的 @ 是程序识别的 Worker 身份，不是依赖 GitHub 账号原生 @：多个 Worker 使用同一认证账号时，GitHub 账号通知不能区分它们。

“私聊”先落实不进公屏、不默认广播的会话路由。若文字仍以明文保存在同一个共享 GitHub 仓库，其他有仓库读取权限的人仍可能读到；它不具有只有双方可读取的权限保证。需要真正保密或严格盲审时，必须另设对应访问控制，不能靠目录名获得。

不预建所有两两会话；第一次私聊时建立。每条消息含稳定 ID、存档、发送者、范围、目标/参与者、话题、回复来源和可选材料引用。重发同一 ID 不重复投递，修改内容必须换新消息或明确更正。同一话题保留因果回复关系，不要求所有私聊争抢一个全局连续序号。

消息保留原始正文，摘要只是索引。普通闲谈不进入所有人模型上下文；实质反驳和前提失效不能被摘要抹去。访问别人桌面、索取材料与回复都能直达准确对象，不让对方重新到全仓猜文件。

## 收信、在线与中断

工作中的 Worker 在启动、自然研究边界、准备使用他人结果或需要协作时检查自己的收件箱，也可以主动查看公屏与访问同行。它应继续独立研究，不能以等待私聊回复代替全部工作，也不把时间花在空轮询上。

保存、投递、实际读取、吸收及执行是不同状态。已读不等于数学上理解或接受，未读不等于拒绝。需要答复的消息保留待办入口，普通信息不强制生成大量回执。收件方结束或不可用时保留消息，用户实际继续对应对话后再处理；消息系统不承诺唤醒 Work。

主 Worker 能转达给本次内部子任务，但跨独立 Work 的暂停和注入仍受实际接口限制。个人“最近活动”只能说明某次记录时间，不能凭心跳缺失推断数学失败或自动销毁工作区。

## 使大规模协作有效的工作流

新 Worker 启动后应自动完成稳定身份和存档绑定、个人桌面准备、必要材料装载、个人未读检查以及准确的读写范围显示。用户不应逐个为它手工建立邮箱或填写大量目录项；用户手动开启 Work 这一动作仍然保留。

研究者目录让每个人查到别人正在使用的数学表示、已有部件与卡点。研究重叠时可以交换材料、合作或继续独立复核，不实行“这条思路已经有人做，其他人禁止做”。跨组发现真实联系时临时做数学比较，不要求先建固定星探常驻编制。

主要协作路径是自主研究、遇到精确缺口时找有关的人、在必要范围讨论、形成可复用材料后发布。重要成果需要更强独立性时，安排干净材料的子任务或由人类另开独立 Work，不能把已经读过原证明的同一上下文改名成盲审者。

仓库维护 AI 仍有必要：维护入口、吸收成熟资产、消除重复正文、修复引用、追踪漏入库成果并记录重要异议。它不逐条批准聊天，也不垄断各队研究方法。既定高水平论文目标用于实际贡献评估，Worker 数量和聊天热度不构成数学价值。

## 现有公屏为什么不能直接扩容

基线代码在 `research/weighted_congestion_frontier/tools/board.py`：`decode` 读取全部事件，`publish` 为单条消息获取当前状态、分配全局序号、重写 `BOARD.md`、向同一个 `wcg/board` ref 推送，随后再读取确认。独立文件可减少正文覆盖，却不能消除同一个 Git ref 的并发更新竞争。

因此，改进不应只是“多造个人目录”。应取消每次发言都重建整块公屏、取消无必要的全局消息序号争用，保留不变消息 ID、因果回复和重试；按收件人/话题索引增量内容，用稳定本地缓存和游标恢复。收件箱宜由不可变消息派生，避免所有发送者同时改收件人的同一个文件。

个人目录之间的独立写入也不解决仓库级推送负载。给每个人另开分支同样不能绕过仓库整体活动限制，本版不恢复“每个 Worker 一条研究分支”。

GitHub 官方建议每仓库最多每分钟 6 次 push，并建议每秒不超过 15 次 Git 读取操作；这都是操作建议，不能说成必然触发的硬截止，也不保证低于推荐值即可支持任意负载。[仓库限制](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits)。

若使用 PAT 调 REST API，通常按用户共享每小时 5000 次额度；内容创建还有一般每分钟 80 次、每小时 500 次的次级限制，部分接口可能更严。这些不是 Git 协议 push 的同一套额度，不得混用。[REST 限制](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)。同仓库 Discussions 的可见性继承仓库，不是逐 Worker 私聊权限。[Discussions 说明](https://docs.github.com/en/discussions/quickstart)。

假设 500 个 Worker，各十分钟只发一条消息，每条单独 push，已是每分钟 50 次 push；若各一分钟用一次 REST 请求收信，单收信即每小时 30000 次。以上是条件计算，不是实际运行测量。它说明现有一条消息一次 Git 写入的方式不能被直接称作高效大兵团通信。

## 两种载体与推荐边界

| 载体 | 可实现什么 | 代价与适用边界 |
|---|---|---|
| 仅 GitHub 的异步版 | 稳定身份、已发布桌面、公屏、逻辑私聊、提及、材料引用、离线消息；程序按范围呈现 | 可先验证协作方式；需要节流、批量、增量缓存，仍有仓库级串行写入和活动负载，不能保证数百 Work 频繁聊天 |
| GitHub 研究资产＋独立的轻量通信服务 | 保持同样身份、桌面和操作入口，消息走有持久存储、索引、幂等与访问控制的独立端点；研究成果仍存 GitHub | 更符合数百研究者频繁通信目标；需要常在线服务、云端 Work 可访问地址、工具接入与实际认证/部署，当前尚未提供也尚未验收 |

对于用户要求的“大规模且高效”，本页建议把后一种作为目标架构，把纯 GitHub 版作为受限试验载体。该建议不是用户已经同意新增服务器；未得到明确选择和可用环境前，不部署服务或声称已有端点。

通信服务只负责消息接收、持久化、路由、查询和真实回执，可以由普通程序执行，不需要一个模型永远当传话领导。它不创建 Work，不负责数学规划，也不迫使各研究者等待中央派单。GitHub 仍是研究资产的长期保存位置，普通聊天的速度不必由数学成果提交速度决定。

聊天确认与 GitHub 保存回执必须分开。消息服务接收到材料提案，不代表该成果已经在 GitHub 或已经被数学审查接受。正式交接、停止或报告远端保存时核对实际提交；服务故障保留本地待发送队列，使用相同 ID 重试。

## 共同成果写入也要避免拥堵

即使聊天移走，若所有 Worker 每个阶段都同时修改相同的总 README、JSON 账本和超图，成果写入仍会冲突。个人桌面先保存带完整身份、版本和来源的候选或已核对部件；共同索引尽量由分项记录生成，集中整理属于材料维护，不是控制研究权。

具体合入程序应核对输入基线、保留双方内容、记录真实冲突，不能因 Git 能合并就认为两个数学条件相容。共同地图的整理可以批量进行，但候选的原始来源、实际状态和新实质反驳不能等到整理时才被看到。避免为了每条普通想法更新全仓登记。

是否采用成果提案队列、由哪些运行中的维护 Worker 整理、怎样维持共同登记一致性，是需要随写入负载一起验证的工程选择，当前不静默更改现有 main 保存合同。

## 原总稿怎样取舍

| 本版优先采用 | 暂不作为前置建设 |
|---|---|
| 精确问题与版本、完整来源、工作集、个人工作区、动态合作、直接求助、公屏与定向通信、失败回收、仓库维护、严格区分数学身份 | 完整桌面壳、运行树画布、所有 subagent 永久房间、全局自动调度、跨 Work 即时控制、复杂固定角色组织、全产品超图数据库重建 |

重大结果的证伪、文献核对和专业贡献评估继续按实际需要组织。总稿中的有用思想在需要时引入，不为了覆盖原稿而给每个普通研究者增加大量管理字段和流程。新的模型、方法与方向仍然开放。

## 施工和验收出口

先确定并实现共同通信合同与个人桌面入口，使一个新 Worker 能完成找人、@、私聊、访问材料、发布和继续研究；不要先重建完整产品外壳。拟议操作包括启动、个人收件箱、公屏、私聊、组聊、访问桌面、发布材料与同步；这些是待实现接口名，不是现有可运行命令。

验证从有限流程开始，再逐步提高真实独立客户端并发与持续负载。验收应分别报告：

- 正常发言、回复、公屏提及、双方私聊、临时组聊、跨存档隔离，以及访问他人已发布桌面是否准确；
- 重复请求、超时后重试、乱序、接收者结束、重启续读、同时发给热点收件人及单个客户端异常是否丢信或误投；
- 给模型的实际阅读量，收件查询成本和新增历史后的开销，是否仍在全量扫描；
- 持续负载下的排队长度、送达延迟分布、错误和限流、重试次数、存储增长与恢复情况；不能只完成一批写入就声称可扩展；
- 研究资产批量提交和共同地图更新是否造成新拥堵、漏收或数学状态误提升；
- Work 实际能够同时执行多少模型工作，与通信程序能够服务多少客户端，必须分别实测。

目前真实环境尚未跑数百独立 Work，也未部署新通信后端。因此不能保证“打开数百 Worker 后立即高效运行”，更不能保证数学成果。应当用以上可测行为证明协作设施可靠，再按实际瓶颈扩展。

## 本轮已做的有限检查

[可复跑本地规格模型](../tests/audits/collaboration/message_routing_model.py)及[实际结果](../evidence/runs/collaboration/message_routing_model.json)核对了 500 个逻辑身份的寻址、个人桌面目录、公开/私聊/组聊路由、提及、跨存档范围、重复发送、非法请求无副作用、离线保留以及读取不自动表示数学采用。

负载公式使用有理数计算并反向核对；另给出在“每轮所有剩余写入者都争抢同一个旧头”这一特定假设下的竞争模型。模型输出不能当成真实 GitHub 吞吐预测。

这些是本地规格与算术检查，不是新聊天系统实现、线上压力测试、权限隔离验证或 Work 平台容量认证。远端保存状态另外核对，不因本文存在就视为已经推送。
